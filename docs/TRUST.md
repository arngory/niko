# Доверенные корни: что чему следует

Состояние на 1.50.0 (2026-11-14). Решения владельца отмечены датой.

## Настройка «Доверенные корневые сертификаты»

Три значения: список Chrome (по умолчанию), список Mozilla, системное хранилище вместе с корнями, установленными
на телефон. Списки Chrome и Mozilla — те, что несёт ядро этой версии приложения (`common/certificate/chrome.go`,
`mozilla.go` в форке ядра; в 1.47.0 — 92 и 161 корень), они меняются с обновлением приложения.

**Списки ядра — не списки браузеров один в один.** Генератор списков в ядре (апстрим sing-box,
`cmd/internal/update_certificates`) берёт их из CCADB и выбрасывает корни, у которых там указана страна или
география «China», — и из списка Chrome, и из списка Mozilla. Поэтому «список Chrome» в приложении — это список
Chrome без таких центров. По ключам корней на ядре `0f84573`: в списке Chrome 92 корня, в списке Mozilla 161,
общих 91.

Настройке следуют:
- исходящие ядра с TLS из Go и uTLS (trojan, vless, vmess, hysteria2, tuic, anytls, shadowtls и др.) и удалённый DNS;
- HTTP-клиент приложения: подписки, наборы правил, обновления, проверка DNS-туннелей (DoT, DoH).

Импортированный `ca.pem` (Маршруты → Ресурсы) добавляется к любому из трёх значений и список не заменяет.
Собственный сертификат профиля и пины ключа действуют поверх настройки, как и раньше.

Полный конфиг sing-box, заданный профилем: если он сам называет список (`certificate.store`), остаётся его список;
если только добавляет сертификаты — получает список из настройки и импортированный `ca.pem` вместе со своими.

## naive

naive — это сетевой стек Chromium внутри библиотеки приложения, и корни он проверяет сам, по своим правилам.
Что он берёт (с 1.49.0, библиотека `arngory/cronet-go` `d5ec437`):

| Настройка приложения | Что берёт naive | HTTP/2 | QUIC |
|---|---|---|---|
| Список Chrome (по умолчанию) | корень должен быть и в списке Chromium, и в списке Chrome приложения | да | да |
| Список Mozilla | корень должен быть и в списке Chromium, и в списке Mozilla приложения | да | да |
| Системные и установленные на телефон | список Chromium и корни телефона (системные и пользовательские) | да | корни телефона — нет |
| любая, у профиля свои пины ключа | список Chromium и пины профиля; список настройки не добавляется | да | да |
| любая, сертификат вписан в профиль | только сертификат профиля, вместо всех списков | да | да |

**Список внутри Chromium шире списка ядра.** По подсчёту серверной сессии по исходникам сборки (Chromium 158,
хранилище корней версии 43): в самом Chromium 99 корней, и девяти из них в списке ядра нет — шесть китайских
(UCA Global G2 Root, UCA Extended Validation Root, vTrus Root CA, vTrus ECC Root CA, GDCA TrustAUTH R5 ROOT,
CFCA EV ROOT), Hongkong Post Root CA 3 и два TrustAsia. До 1.50.0 naive без пинов и без своего
корня принимал сертификаты этих центров, а остальное ядро при «списке Chrome» — нет. Вырезать корни из самой
сборки Chromium нельзя: изменится содержимое расширения trust_anchors в ClientHello, то есть отпечаток. С 1.50.0
это выровнено пинами (см. ниже): три из девяти (Hongkong Post Root CA 3 и два TrustAsia) есть в списке Mozilla
ядра и при «Mozilla» проходят, при «списке Chrome» не проходит ни один.

Как это устроено:
- Chromium на Android читает корни помимо списка Chrome только из файла, названного переменной `SSL_CERT_FILE`.
  Приложение называет ему файл один раз при запуске процесса (`libcore/naive_roots.go`) и перед каждым запуском
  ядра записывает в него корни телефона (при «системных») или оставляет пустым. Файл читается при создании
  движка, поэтому смена настройки действует с перезапуска ядра.
- До 1.49.0 (библиотеки 154 и первая 158) Chromium сам читал системный каталог Android
  (`/system/etc/security/cacerts`) при любой настройке.
- Корни из файла Chromium считает «локально доверенными»: по HTTP/2 принимает, по QUIC — нет, там нужен корень из
  списка Chrome. Так ведёт себя и сам Chrome.
- Сертификат в поле профиля **заменяет** список (так устроен вызов библиотеки) и переводит проверку в упрощённый
  режим: без прозрачности сертификатов (CT) и ограничений Chrome на корни. Для своего сервера под своим корнем это
  ожидаемо.
- Пины ключа (`niko-pin`, поле «Пиннинг сертификата») проверяются вместе с цепочкой, а не вместо неё.

Проверено на эмуляторе Android 14 с библиотекой из APK (job `e2e`, run 43639852769; корень стенда установлен как
пользовательский):
- список Chrome, профиль без сертификата → отказ, «cert authority invalid»;
- «системные» → по HTTP/2 сервер принят; по QUIC ни один запрос не прошёл, «quic protocol error» (так Chromium
  обрывает сессию с корнем, которого не знает);
- обратно на список Chrome → снова отказ: файл корней опустошается;
- с корнем в профиле → работает по HTTP/2 и по QUIC;
- публичный сайт (www.gstatic.com как «сервер naive») при списке Chrome → сертификат принят, дальше ответ 400 на
  CONNECT, как и должно быть у не-прокси;
- в журнале устройства нет жалобы Chromium на пустой файл корней.

Не проверено на устройстве: что Chromium действительно перестал читать системный каталог Android. Корня, который
лежал бы только там и под который есть сертификат сервера, на стенде нет; это следует из кода сборки и из теста
серверной сессии на Linux.

### Как naive держится списка настройки

Дать Chromium другой список можно только тем же вызовом, что и сертификат профиля: он заменяет список Chromium и
отключает CT и ограничения Chrome на корни; кроме того, клиент продолжал бы объявлять серверу корни Chrome
(расширение trust_anchors), а проверял бы по другому списку, и QUIC стал бы доверять всем корням списка. Поэтому
список не подменяется, а сужается: Chromium проверяет штатно, а ядро дополнительно ставит профилю пины ключа —
SHA-256 ключей всех корней списка из настройки (`certificate.StorePublicKeyHashes` в ядре, `protocol/naive`). В
проверенной цепочке должен быть ключ одного из них. Отпечаток не меняется, CT и ограничения Chrome остаются.

Правило не действует:
- если у профиля свои пины (`niko-pin`, поле «Пиннинг сертификата»): они строже и остаются одни, иначе пин листа
  размывался бы любым корнем списка;
- если у профиля свой сертификат: он вне всех списков;
- при «системных»: корни телефона ни в одном списке не числятся;
- если сервер задан адресом, а не именем: Chromium пинит имя.

Когда правило действует, ядро пишет в журнал строку «the server's chain is held to the N roots of the … list
besides Chromium's own». Сервер, который Chromium принял бы, а список не принимает, отклоняется с «ssl pinned key
not in cert chain».

### Решено владельцем (2026-11-14)

1. По умолчанию naive доверяет только списку Chrome; доверие системным корням — опция. Сделано в 1.49.0: опция —
   значение «системные» общей настройки.
2. Импортированный `ca.pem` на naive не действует, и делать это не будем: свой корень для naive-сервера
   вписывается в поле сертификата профиля. Это известный пробел, а не ошибка.
3. «Mozilla» для naive — пересечение списков; затем общее правило: профиль naive без пина ноды и без своего корня
   держится списка из настройки и при «списке Chrome» (переданы серверной сессией). Сделано в 1.50.0.
4. Отдельный переключатель, по умолчанию выключенный: при «системных» принимать корни телефона и по QUIC. Не
   сделано: ждёт сборки библиотеки.

## Известные пробелы

- `ca.pem` не действует на naive (решение 2 выше).
- При «системных» корни телефона работают в naive по HTTP/2, но не по QUIC (до переключателя, решение 4).
- Сервер naive, заданный адресом без имени, списка настройки не держится: Chromium пинит только имя.
- Сертификат в профиле naive отключает CT и ограничения Chrome для этого профиля.
- Список Chromium меняется с версией библиотеки, списки ядра — с версией ядра; расхождение между ними считает
  тест ядра (`TestNekoChromeListLeavesOutChromiumOnlyRoots`), и его надо пересчитывать с каждой новой библиотекой.
- Соединения приложений пользователя через туннель проверяют сами приложения; настройка на них не влияет.
