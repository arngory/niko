# Минута без связи на первом контакте в Yggdrasil (#109)

Почему 14 ноября шаг LAN interop «phone → laptop, the laptop open to all» дважды не дождался ответа за 120 с, хотя
обычно отвечает за секунды. Причина не в узле и не в фильтре niko-server, а в ironwood: первый контакт двух узлов
Yggdrasil иногда стоит ровно минуту.

## Что было в CI

С 2026-11-14 по 2026-11-21 interop шёл 199 раз, LAN-тест прошёл около 175 раз. Падения в этом шаге — только два прогона
14 ноября (43612133040 и первая попытка 43613048478), оба на коде теста до `d2cc997`: тот начинал звонить ноутбуку сразу
после его перезапуска, не дожидаясь связи с узлом. Третье падение LAN-теста (19 ноября) — паника записи в закрытое
устройство Yggdrasil, её исправило ядро `6455bf6`.

## Опыт

Чистый yggdrasil-go (форк `5afe92f`, ironwood `0712ecc` — текущий upstream), без узла raycontrol и niko-server: хаб и
листья на 127.0.0.1 по TLS, обмен пакетами через `core.WriteTo`/`ReadFrom` (сессии и pathfinder ironwood). Телефон шлёт
ноутбуку пакет раз в секунду, ноутбук отвечает эхом.

| | Первый контакт за 0–9 с | Ровно ~60 с |
|---|---|---|
| ironwood `0712ecc` | 25 из 30, 17 из 20 | 5 из 30, 3 из 20 |
| с исправлением ниже | 30 из 30 | 0 |

Перезапуск ноутбука с тем же ключом (сценарий теста: «закрытый» экземпляр, потом открытый и рядом устройство другого
пользователя) — 3–6 с и с исправлением, и без него.

## Механизм

Во время зависания у телефона есть путь к ноутбуку, но нет сессии (только буфер с init); у ноутбука есть сессия с
телефоном, но нет пути к нему.

1. Телефон шлёт init (`_bufferAndInit`), ноутбук создаёт сессию и один раз отвечает ack.
2. Пути к телефону у ноутбука ещё нет: ack ждёт в rumor-кэше, а единственный lookup теряется, пока дерево сходится
   (корень — наименьший ключ — меняется по мере подключения узлов, путь `from` в lookup успевает устареть).
3. Телефон повторяет тот же init с тем же `seq` с каждым пакетом. `sessionInfo.handleInit` отбрасывает его
   (`init.seq <= info.seq`): ack не повторяется, ноутбук больше ничего не шлёт, нового lookup нет.
4. Всё стоит, пока через `sessionTimeout` (1 мин) не истечёт сессия ноутбука; следующий init заводит новую.

Два таких зависания подряд (закрытый экземпляр, потом открытый) — больше 120 с, как 14 ноября. С `d2cc997` тест ждёт
связи ноутбука до первого звонка и не попадает на это, но сама минута осталась: её видят пользователи LAN-v1 и строк
Yggdrasil при первом соединении.

## Исправление

`encrypted/session.go`, `handleInit`: на повтор того же init (`init.seq == info.seq`) отправить заново тот же ack, что и
в первый раз (`info.ack`), и только пока от отправителя по сессии ничего не пришло (`info.rx == 0`); старый (`<`)
по-прежнему отбрасывать. Трафик ack сам заново ищет путь (rumor, не чаще раза в секунду). Тот же, а не свежий ack:
отправитель, у которого сессия уже есть, отбросит его по `seq` и не сдвинет ключи, так что переигранный init (дубль в
сети или чужой повтор) не держит сессию в постоянном пересогласовании.

```go
if init.seq < info.seq {
	return
}
if init.seq == info.seq {
	if info.rx == 0 && info.ack != nil {
		info.mgr.sendAck(&info.ed, info.ack)
	}
	return
}
```

Нужен в ironwood и ядра (телефон, компьютер), и niko-server: в соединении устройства с узлом init принимает узел.

Сделано в форке [arngory/ironwood](https://github.com/arngory/ironwood), `88ef67c`, с двумя тестами:

- `TestRepeatedInitIsAckedAgain`: первый ack теряется (кадры трафика от получателя пропадают, пути и связь целы),
  повтор init должен дать его снова. Без исправления падает (B не слышит A 10 с), с ним проходит 20 из 20;
- `TestReplayedInitKeepsKeys`: после рукопожатия тот же кадр init повторяется дважды, ключи отправителя не должны
  сдвинуться. Первый вариант исправления (свежий ack на каждый повтор, `4e588c9`) он ловит: ключи 1 → 3.

libcore берёт форк через `replace`; niko-server подключает его сам. В upstream не отправляли (решение владельца
2026-11-21): ironwood по README — pre-alpha, без стабильного API; открытые PR там о том же не говорят, но два трогают
`encrypted/` (окно повторов nonce, постквантовые сессии) — при их подтягивании возможен конфликт.

### Открытые PR upstream

Просмотрены 2026-11-21; ни у одного нет ответа сопровождающих.

- **Arceliar/ironwood#53, окно повторов nonce** (lostmsu): перенесён в форк как есть, `6599008`, с автором.
  - Раньше приём сессии брал только nonce выше самого старшего, и пакет, переставленный в пути, терялся. Теперь
    окно на 8128 nonce, как в WireGuard и RFC 6479; 1 КиБ на сессию.
  - Повтор по-прежнему отклоняется. nonce отмечается только после того, как пакет расшифрован.
  - Меняется только приём, формат на проводе тот же, и узлы без правки его не замечают.
  - Наш тест `TestReorderedTrafficArrives` (`f70babd`): два пакета меняются местами на канале. Без окна первый
    теряется, с окном оба приходят по одному разу.
- **Arceliar/ironwood#48, гибридные постквантовые сессии** (neilalexander): не перенесён.
  - init уходит через HPKE с ML-KEM-768 + X25519, трафик — на ChaCha20-Poly1305 вместо NaCl box. Добавлен новый тип
    пакета, а номер типа трафика сдвинут с 3 на 4. Переговоров о версии нет.
  - Узел с этой правкой не поймёт ни одного узла без неё: ни публичные узлы Yggdrasil, ни yggstack в проверках, ни
    другие устройства пользователя.
  - Брать его стоит, только когда сеть Yggdrasil перейдёт на него целиком (выпуск yggdrasil-go с ним), и вместе с
    niko-server.
