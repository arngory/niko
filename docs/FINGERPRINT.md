# Отпечаток TLS: как держать его равным настоящему Chrome (блок B2)

## 1. Проблема

- В ядре `chrome` — это `utls.HelloChrome_Auto`, то есть `HelloChrome_133` в metacubex/utls v1.8.7.
- REALITY, VLESS-TLS, Trojan, AnyTLS и `tls://`-пиры Yggdrasil показывают DPI этот ClientHello.
- С тех пор Chrome изменился. Снимок Chrome for Testing 153 (`scratchpad/chcap`, 2026-11-04) отличается от
  uTLS Chrome 133:
  - `signature_algorithms`: впереди GREASE и ML-DSA-44/65/87 (`0x0904`–`0x0906`). У uTLS их нет. По открытым
    источникам ML-DSA появился в Chrome 150, GREASE в этом списке — в Chrome 152, и он меняется от соединения к
    соединению.
  - Два новых расширения:
    - `0xca34` (`trust_anchors`, Trust Anchor IDs), 186 байт;
    - `0x12e0`, 2 байта, не зарегистрировано, по источникам появилось в новых версиях.
  - Набор шифров, группы и `key_share` (GREASE, X25519MLKEM768, X25519), ALPS `0x44cd`, сжатие сертификата
    (brotli) — как у uTLS.
- Итог: JA4 отличается и числом расширений, и хешем списка подписей. Снаружи такой клиент — «Chrome 133 через
  полтора года после выхода», то есть редкий отпечаток. В обсуждении Xray #7131 Chrome 133 называют одним из
  отпечатков, которые режет ТСПУ.

## 2. Почему не BoringSSL напрямую

- **REALITY.** Нужно управлять `session_id`: туда кладётся зашифрованная метка. Ещё нужен доступ к ключам
  рукопожатия до отправки ClientHello. Готовый стек Chromium/BoringSSL этого не даёт. Свой BoringSSL через cgo
  означает переписать клиент REALITY и потерять кросс-сборку gomobile.
- **naive.** Для него BoringSSL как раз правильный путь. В форке ядра уже есть исходящий `naive` на cronet-go
  (сетевой стек Chromium). Это стек Chrome, а не его копия; на сборке SagerNet (154) ClientHello отличался от
  Chrome, на собственной сборке 158 форма совпала: замеры 2026-11-14 ниже. Цена: статическая
  libcronet около 65 МБ на ABI до линковки. В APK после strip, по оценке, +8–12 МБ на ABI. Это заменит плагин naive
  (ревью S8: доверие плагинам по префиксу) и уберёт отдельный процесс. Нужна проверка размера и поведения на
  Android.

## 3. Решение для uTLS: эталон с настоящего Chrome, а не ручной профиль

1. **Снимок.** В CI (`fingerprint.yml`) запускается Google Chrome stable на раннере. Нужен обычный режим под xvfb,
   а не headless: в headless-сборке нет ECH GREASE (проверено на CfT 153 с `/etc/hosts`). Chrome открывает
   `https://<имя>:<порт>/` на локальном слушателе, тот сохраняет сырой ClientHello.
2. **Профиль в ядре.** Сырой ClientHello хранится в форке (`common/tls/chrome_hello.hex`) вместе с версией Chrome.
   Для `chrome` ядро строит `ClientHelloSpec` через `utls.Fingerprinter` и применяет его через `HelloCustom` +
   `ApplyPreset`. Действует для обычного uTLS и для REALITY.
   - Порядок расширений перемешивается при каждом соединении, как у Chrome (`ShuffleChromeTLSExtensions`).
   - GREASE (шифры, группы, версии, расширения, ECH и подписи) свой на каждое соединение. GREASE в подписях
     `Fingerprinter` сохраняет литералом, нужна правка в нашем utls.
   - `key_share`, `random` и `session_id` новые на каждое соединение. Для REALITY `session_id` задаёт клиент.
   - `trust_anchors` и `0x12e0` — константные данные из снимка: у всех Chrome этой версии они одинаковы.
   - Фильтр ALPN как сейчас: у REALITY `h2`/`http/1.1` по снимку. Где ALPN задан явно, он меняется в спецификации.
3. **Проверка равенства.** Go-тест в CI соединяет клиент ядра `chrome` с тем же слушателем. Затем JA4 (GREASE
   вычищен) и отсортированный набор расширений с длинами сравниваются со снимком Chrome. Несовпадение — CI красный.
4. **Слежение.** Раз в неделю по расписанию задача снимает свежий Chrome stable. Если JA4 изменился, задача
   падает и прикладывает новый `chrome_hello.hex`: остаётся закоммитить его в форк и выпустить ядро.

## 4. Что ещё в B2

- Отдельная настройка «Отпечаток» для REALITY не нужна: в REALITY-ссылках `fp=chrome`, его и заменяет эталон.
  Отпечатки `firefox`, `safari` и `ios` остаются из uTLS как есть. По ним новых данных нет.
- `tls://`-пиры Yggdrasil в ядре уже берут `chrome`, эталон применится и к ним.
- naive через cronet: собрать ядро с `with_naive_outbound` на всех ABI, сравнить размер APK, прогнать interop
  `naive` против `rayd` (job уже есть) и заменить плагин, если размер приемлем.
- SPA в форме ClientHello (spa-v2 §10.1, raycontrol v0.10.0) строится тем же эталоном. Тогда стук по TCP выглядит
  как начало TLS от этого же Chrome.

## 5. Сделано в 1.27.0

- **Эталон в форке ядра.**
  - Пакет `common/tls/chromehello`: файл `hello.hex` (сырая запись ClientHello) и `SOURCE` (браузер и дата снимка).
  - `Spec()` даёт новый spec на каждое соединение. `Shape()` и `JA4()` сравнивают два ClientHello без
    случайных частей.
  - `chrome` и его псевдонимы (`chrome_psk*`, `chrome_pq*`) в uTLS, REALITY и `tls://`-пирах Yggdrasil строятся
    из эталона. Для REALITY это то же: `session_id` задаёт клиент REALITY, ключевые доли проверяет его `key_share`.
- **Эталон** — Google Chrome 156.0.8078.47 stable, снятый в CI `fingerprint.yml` на раннере (первый прогон,
  2026-11-04). JA4 `t13d1517h2_8daaf6152771_cb7bf5808d99`.
  - С ECH GREASE (`0xfe0d`), своим набором `trust_anchors`, без `0x12e0`.
  - `0x12e0` и отсутствие ECH GREASE — особенности Chrome for Testing: первый локальный снимок CfT 153 давал
    `t13d1517h2_…_344585cda68d`.
  - Для сравнения, uTLS Chrome 133 даёт `t13d1516h2_…`: другое число расширений и другой хеш подписей.
- **Проверки.**
  - Тест форка (`chromehello_test.go`): форма и JA4 ClientHello ядра совпадают со снимком; порядок расширений,
    GREASE (и в подписях) и ключи меняются от соединения к соединению; для адреса нет SNI.
  - `fingerprint.yml` в Niko (`libcore/chromecheck`). Google Chrome stable на раннере в обычном режиме под Xvfb:
    - клиент ядра шлёт ту же форму, что эталон;
    - Chrome шлёт то же, что эталон, иначе задача падает.
  - Запуск — при смене пина ядра и раз в неделю. Свежий снимок — в артефакте `chrome-hello`.
- **Как обновить эталон.** Взять `hello.hex` и `SOURCE` из артефакта `chrome-hello`, положить в
  `common/tls/chromehello` форка, закоммитить, закрепить коммит в `buildScript/lib/core/get_source_env.sh`.
- **SPA в форме ClientHello** (spa-v2 §10.1) строится тем же эталоном: SNI нет (обращение по адресу), пакет —
  данные `session_ticket`. JA4 у него `t13i1516…` с теми же хешами, что у эталона.
- **Открыто.**
  - `trust_anchors` в эталоне — константа из снимка. Если Chrome меняет порядок или набор от соединения к
    соединению, еженедельная проверка это покажет: тогда понадобится перемешивание, как для расширений.
  - naive через cronet — замер 2026-11-04. arm64, cronet-go `c10c03c` и форк ядра `33d0c2a` с тегом
    `with_naive_outbound`:
    - `libgojni.so`: 35,5 → 45,9 МБ, то есть +10,4 МБ после установки;
    - в APK `.so` сжаты (`useLegacyPackaging`): +4,7 МБ к загрузке, arm64 APK 18,7 → около 23,4 МБ.

    Взамен:
    - TLS и HTTP/2 от сетевого стека Chromium (сравнение с Chrome — замеры 2026-11-14 ниже);
    - нет отдельного APK плагина и его процесса;
    - закрывается S8 (доверие плагину по префиксу authority).

    Включено в 1.29.0 (B4):
    - сокеты cronet открывает dialer ядра (`cronet.NaiveClientOptions.Dialer`) и передаёт cronet их копию: protect
      VPN, стук и detour действуют как у остальных исходящих;
    - interop с `rayd naive` за фронтом niko-server по h2 и QUIC — в `raycontrol-interop.yml`, сборка для Linux
      через clang и lld;
    - профили naive строятся как исходящий ядра (`fmt/naive/NaiveFmt.kt`), плагин больше не нужен.

    Замер 2026-11-14, job `naive` в `raycontrol-interop.yml` (run 43613048478): первая запись TLS исходящего naive
    (ядро `ee7150e`, libcronet 154.0.8037.49 из сборки SagerNet) против эталона из ядра (Chrome 156.0.8078.47,
    `common/tls/chromehello`), скрипт `.github/scripts/hello.py`.
    - Совпадает всё, что не меняется от соединения к соединению: шифры, группы, алгоритмы подписи, версии, ALPN,
      ALPS и остальные расширения.
    - **Отличие одно: исходящий не шлёт `trust_anchors` (0xca34).** Chrome шлёт его в каждом ClientHello (186 байт
      в эталоне). Причина, по разбору серверной сессии: в слое Cronet список идентификаторов корней пуст, его
      заполняет только программа `naive`; в библиотеку из сборки SagerNet это не перенесено. То же касается QUIC
      Initial (не снималось).
    - Следствие: по первому пакету исходящий naive отличим от Chrome. Называть его «отпечатком Chrome» нельзя, пока
      библиотека не исправлена. Исправление — в переносе на Chromium 158 (форк `arngory/naiveproxy`); после него
      тот же шаг interop должен перестать предупреждать, и предупреждение можно сделать ошибкой (`--strict`).
    - Сравнение — предупреждение, а не падение: версии Chromium в библиотеке и снятого Chrome разные.

    Замер 2026-11-14 после перехода на Chromium 158, тот же шаг (run 43627950276): ядро `0116823`, libcronet
    158.0.8127.36 из собственной сборки (`arngory/naiveproxy` `aea0d1d`, `arngory/cronet-go` `036584d`), эталон
    прежний (Chrome 156.0.8078.47).
    - **Форма ClientHello совпала с Chrome: 16 частей, набор расширений тот же, `trust_anchors` (0xca34) есть.**
      Предупреждений шаг не дал.
    - Сравнивается форма первой записи TLS (состав и порядок неизменяемых частей), а не байты: случайные поля,
      GREASE и порядок расширений, который Chrome перемешивает, у каждого соединения свои.
    - Сравнение остаётся предупреждением и после совпадения: эталон следует за стабильным Chrome сам
      (`fingerprint.yml`), а библиотека меняется только пересборкой, так что между ними возможен разрыв в версию,
      и красный interop на каждый чужой коммит в это время ничего не даст.
    - Не снято на стороне клиента: QUIC Initial исходящего (серверная сессия сообщает совпадение с Chrome 158 на
      Linux по TLS и по QUIC Initial); захват с Android (ни TLS, ни QUIC).
    - На Android библиотека из APK исполнена (эмулятор, job `e2e`, run 43630273426): naive против `rayd naive` по
      HTTP/2 и по QUIC с корнем в профиле работает, без корня в профиле отклоняет сервер под корнем из
      пользовательского хранилища.
    - **ClientHello с Android снят** (эмулятор Android 14 x86_64, job `e2e`, run 43639852769, библиотека `d5ec437`
      из APK): первая запись TLS профиля naive к порту на раннере, тот же скрипт и тот же эталон. Форма совпала с
      Chrome: 16 частей, набор расширений тот же, `trust_anchors` есть. Эталон — Chrome для Linux, не Chrome для
      Android: с настоящего телефона и с Chrome для Android ничего не снималось. QUIC Initial не снимался нигде.
