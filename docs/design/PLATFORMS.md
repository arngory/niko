# Niko: один дизайн на всех платформах

Вопрос владельца (2026-11-16): как привести всё под один дизайн и насколько нативным выйдет приложение — Android
нативно, а Windows, Linux и macOS на Flutter, или Flutter везде; и не вынести ли десктоп в отдельный репозиторий.

Это предложение, решение за владельцем. Числа сняты с кода 2026-11-16.

## Коротко

- **Цель — Flutter везде, Android переводим последним.** Один код экранов даёт один дизайн по построению, а не по
  дисциплине.
- **Нативным остаётся то, что и должно быть нативным:** всё, чем приложение держится за систему. Экраны нативными не
  нужны: дизайн у нас свой и одинаковый везде, системных виджетов в нём нет.
- **Android не ждёт переноса логики в Go.** Экраны на Flutter говорят с одним API (`NikoService`); на Android его
  сначала отдаёт тонкая прослойка над нынешним Kotlin.
- **Сейчас — дешёвая перекраска нативного Android** (цвета, шрифт, знак), без переделки экранов: их заменит Flutter.
- **Один репозиторий** до конца переноса логики. Десктоп отдельно — только вместе с выносом общего ядра.

## Варианты

**А. Android нативно, компьютер на Flutter.** Два кода экранов навсегда.

- Плюсы: Android обновляется по экрану за релиз, без большого переписывания; привычные инструменты и тесты.
- Минусы: каждый экран (их около сорока) и каждая новая функция делаются и ревьюятся дважды, на Kotlin и на Dart.
  Единый дизайн держится только на дисциплине: общие токены, одинаковые имена компонентов, сверка скриншотов.
- Чтобы экраны Android совпали с макетами, их всё равно придётся переписать (с Views на Compose): перекраской нижнюю
  панель, виды «Простой» и «Расширенный» и новые строки не получить.

**Б. Flutter везде.** Один код экранов для Android, Windows, Linux и macOS.

- Плюсы: экран и функция делаются один раз; компоненты, тема, тексты и состояние общие. У телефона и компьютера
  раскладки разные (нижняя панель против шапки с разделами), это два набора экранов в одном проекте, но из одних
  виджетов.
- Минусы и цена:
  - экраны Android переписываются целиком, старые 12 400 строк уходят;
  - APK вырастет примерно на 5–6 МБ на архитектуру (сейчас около 29 МБ), процесс окна займёт на десятки мегабайт
    памяти больше нативного; на службу VPN это не влияет, она в своём процессе;
  - проверки на эмуляторе (`e2e.sh` читает экран через `uiautomator`) нужно перевести на тесты Flutter;
  - переводы из `strings.xml` (20 языков) переносятся скриптом в формат Flutter;
  - для ТВ фокус пульта настраивается вручную.

**Рекомендация — Б, по шагам ниже.** Довод против А решающий: при одном владельце и четырёх платформах двойная работа
над каждым экраном дороже одного переписывания.

## Что остаётся нативным при Flutter везде

| Платформа | Нативно (не Flutter) | Окно |
|---|---|---|
| Android | Служба VPN, постоянное уведомление, плитка и ярлыки, автозапуск, список приложений и их значки, Keystore и подтверждение приложения (app-attest), разрешения, камера QR, лаунчер ТВ, плагины — Kotlin, как сейчас | Flutter |
| Windows | Служба, TUN, системный прокси, проверка подписи клиента (`boxdd`, Go); установщик NSIS; трей и автозапуск через плагины | Flutter |
| Linux | `boxdd` уже есть (polkit); трей через appindicator; пакеты deb и AppImage | Flutter |
| macOS | Демона нет: нужен либо Network Extension на Swift, либо порт `boxdd` с launchd | Flutter |

**macOS — отдельный этап и отдельные расходы.** Без подписи Developer ID и нотаризации Gatekeeper по умолчанию
приложение не запускает: пользователь должен сам разрешить его в настройках системы, а Network Extension без такой
подписи не загрузится вовсе. Самоподписанный сертификат, как на Windows, тут не помогает. Developer ID — это Apple
Developer Program, 99 $ в год. Решение о macOS — за владельцем, после Windows и Linux.

## Как Android не ждёт Go

Сейчас план десктопа такой: логика переносится из Kotlin в Go (`NikoService`), потом Android переходит на неё.
Если экраны Android на Flutter ждут этого переноса, новый вид телефона откладывается на весь перенос.

Развязка — API раньше реализации:

1. `NikoService` описывается в proto один раз. Экраны Flutter знают только его.
2. На компьютере его отдаёт Go в демоне (gRPC), как и задумано.
3. На Android его сначала отдаёт прослойка на Kotlin поверх нынешней логики: те же сообщения proto идут через
   двоичный канал Flutter. Логика не переписывается, только заворачивается.
4. Golden-тесты сравнивают Kotlin и Go за одним API. Когда совпали — Android переключается на Go, прослойка уходит.

Проверить на этапе 2b вместе со связкой Flutter ↔ `boxdd`: один экран (главная) на Flutter под Android через
прослойку. Если прослойка окажется дороже ожидаемого, остаётся вариант А для Android.

## Порядок

| Шаг | Что | Когда готово |
|---|---|---|
| 1 | Перекраска нативного Android: цвета и шрифт из токенов, знак, короткие подписи. Экраны не переделываются | один релиз |
| 2 | Этап 2b десктопа: Flutter ↔ `boxdd` на Windows; тот же экран под Android через прослойку | главная работает на обеих платформах |
| 3 | `NikoService` в proto; экраны Flutter по макетам, телефон и компьютер из одних виджетов | экраны сверены с холстом по ID |
| 4 | Android на Flutter выходит в канале предварительных сборок (`preview`), стабильный остаётся нативным | нет расхождений с нативным по функциям из описи |
| 5 | Windows, затем Linux: установщик, подпись, трей | релиз с проверкой, как у APK |
| 6 | Android на Flutter становится стабильным; нативные экраны удаляются | один релиз без откатов |
| 7 | Логика на Go за тем же API; macOS — если решено | golden-тесты Go = Kotlin |

Токены в обоих случаях берутся из одного `tokens.json` дизайн-системы: из него генерируются тема Flutter и, для шага 1,
ресурсы Android.

## Репозиторий

**Сейчас не делить.** Экраны на Flutter — общий код Android и компьютера, отдельного «десктопа» в варианте Б нет.
Что держит всё вместе:

- общий Go (`libcore`: подписка узла, API, пробы, minisign) нужен и APK, и демону;
- golden-тесты сравнивают Kotlin и Go в одном прогоне CI;
- одни проверки совместимости с raycontrol и одна настройка подписи релизов.

Раскладка в этом репозитории: `client/` — проект Flutter (в нём же `android/` с нынешним Kotlin), `libcore/` — Go,
`libcore/cmd/nikod` — демон.

**Когда делить имеет смысл:** после шага 7, если понадобятся отдельные теги и выпуски или отдельная лицензия. Тогда
три репозитория: ядро (Go), клиент (Flutter со всеми платформами), и связывает их закреплённая версия ядра, как
сейчас с форком sing-box. Цена — три коммита на одно сквозное изменение вместо одного.

Про лицензию отдельно: код, выросший из NekoBox и sing-box, остаётся под GPL-3.0, куда бы он ни переехал; экраны на
Flutter — целиком наш код, и только для них выбор лицензии свободен. Это довод за отдельный каталог или репозиторий
клиента, но решается он в разговоре о лицензиях, не здесь.

## Что решить владельцу

1. Вариант Б (Flutter везде, Android последним) или А (Android нативно навсегда).
2. macOS: делать ли, с учётом 99 $ в год и отдельного демона.
3. Перекраска нативного Android сейчас (шаг 1) — да или ждать Flutter.
