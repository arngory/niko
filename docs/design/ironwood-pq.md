# Постквантовые сессии ironwood с откатом на классику

Статус: черновик дизайна, до кода. Согласуется с сервером (niko-server, raycontrol) и владельцем. Решение владельца
(2026-11-21): гибридные сессии из Arceliar/ironwood#48 переносятся в наши форки arngory/ironwood и
arngory/yggdrasil-go с откатом на классические сессии для чужих узлов. Сервер подтвердил решение у владельца напрямую.

## 1. Что берём из Arceliar/ironwood#48 и что меняем

**Берём криптографию как есть:**
- init и ack запечатываются HPKE с ML-KEM-768 + X25519 (`crypto/hpke`, `crypto/mlkem`, Go 1.26+). X25519-часть —
  статический ключ получателя, выведенный из его ed25519-ключа, как в классике. ML-KEM-ключ — эфемерный ключ
  процесса получателя, он объявляется пакетом PQInfo;
- init подписан статическим ed25519-ключом отправителя, с отдельным контекстом подписи (`ironwood-init-v2`);
- в init идёт случайный `ratchetSecret` (32 байта), он подмешивается в ключи трафика (SHA-256);
- трафик сессии — ChaCha20-Poly1305 вместо NaCl box;
- PQInfo: ML-KEM-ключ процесса и его номер (`seq` = время запуска), подписанные ed25519-ключом (`ironwood-pqinfo-v2`).

**Меняем, чтобы не ломать сеть:**
- Номера типов пакетов. В #48 PQInfo встаёт на 3, а трафик сдвигается на 4, и узел без правки понимать перестаёт.
  У нас классические типы остаются прежними байт в байт, новые идут после них:

  | Тип | Классика (как сейчас) | Постквант (новое) |
  |---|---|---|
  | 0 | dummy | — |
  | 1 | init | — |
  | 2 | ack | — |
  | 3 | traffic | — |
  | 4 | — | PQInfo |
  | 5 | — | PQ init |
  | 6 | — | PQ ack |
  | 7 | — | PQ traffic |

  Узел без правки незнакомый тип молча отбрасывает (`handleData`, ветка `default:`) — проверено сервером на
  f70babd. Флаг в классическом init не годится: `sessionInit.decrypt` требует точного размера, а `seq` — время
  Unix, по нему сессии упорядочиваются.
- Отдельный тип трафика (7), а не тип 3 с другим шифром: узел, который ошибся в типе сессии собеседника, получает
  незнакомый тип и не пытается его расшифровать не тем ключом.
- Окно повторов nonce (Arceliar/ironwood#53, у нас f70babd) работает и для PQ-трафика.
- Исправление повторного init (88ef67c: повторный init получает тот же ack, пока трафика не было) переносится и на
  PQ init.

## 2. Переговоры

У каждого ключа собеседника своя политика:

- **Обязательно PQ** (`requirePQ`):
  - ключ узла, для которого подписка объявила постквант (§4);
  - на узле — ключ устройства, для которого `users_file` объявил постквант (§4);
  - любой ключ, с которым в этом процессе уже была PQ-сессия (липкая память, §3).
- **По возможности** — все остальные: чужие узлы Yggdrasil, устройства без объявления.

**Первый контакт, «по возможности».** Узел с правкой шлёт PQInfo и классический init вместе.
- Узел без правки отбрасывает PQInfo и отвечает на классический init как сейчас. Задержки нет.
- Узел с правкой видит PQInfo, запоминает ML-KEM-ключ отправителя и отвечает своим PQInfo. Классическую сессию он
  при этом может уже поднять: трафик идёт сразу.
- Как только оба узнали PQInfo друг друга, инициатор шлёт PQ init. PQ-сессия заменяет классическую: в карте
  сессий одна запись на ключ. Ключ становится липким, обратно на классику для него — только после перезапуска
  процесса (или никогда, если память на диске, §3).
- Пакеты классической сессии, ушедшие до замены, могут потеряться: TCP перешлёт.

**Первый контакт, «обязательно PQ».** Классика не шлётся и не принимается совсем.
- Отправитель шлёт PQInfo и ждёт PQInfo собеседника. Данные лежат в буфере сессии, как сейчас при ожидании ack.
- Классический init, ack и трафик от этого ключа отбрасываются.
- Нет ответа — соединения нет, как при недоступном узле, а не тихий переход на классику.

**Почему так, а не «PQ, а по тайм-ауту классика».** Тайм-аут даёт человеку в середине понижение: он выбрасывает
PQInfo, и стороны сходятся на классике. «По возможности» понижение для первого контакта тоже даёт, но только там,
где нам не на что опереться (чужой узел, первая встреча). Для пары узел↔устройство, то есть почти для всего
трафика выходов, его закрывает объявление по каналу, которому уже верят (§4).

**Что видно на проводе.** PQInfo ~1,25 КБ, PQ init и ack ~2,5 КБ (HPKE enc 1120 Б, ML-KEM-ключ 1184 Б, подпись,
поля). Это один раз на сессию и при ротации ключей; MTU Yggdrasil (65535) их пропускает, нижние связи — потоки.

## 3. Липкая память

- В памяти процесса: множество ключей, с которыми была PQ-сессия. Ключ из него получает политику
  «обязательно PQ» до конца процесса.
- Позже — на диске устройства (файл рядом с ключом Yggdrasil), со сроком, например 30 дней с последней PQ-сессии:
  иначе собеседник, который откатил свою версию, станет недоступен навсегда.
- Первую встречу память не защищает; для своих узлов это делает §4.

## 4. Объявление способности (контракт raycontrol, согласуется отдельно)

- **Узел → устройство.** В подписке у строки Yggdrasil — признак, что узел ждёт PQ от своих устройств. Например,
  параметр `pq=1` в ссылке Yggdrasil. Клиент передаёт ключ узла в ядро списком «обязательно PQ».
- **Устройство → узел.** Устройство сообщает узлу, что умеет PQ (поле в регистрации или обновлении устройства,
  например `yggdrasil_pq: true`). raycontrol пишет в `users_file` у ключа устройства `yggdrasil.pq: true`, и узел с
  этим ключом классику больше не принимает.
- Включение — по шагам: сначала обе стороны умеют PQ и объявляют, но держат «по возможности»; после проверки в
  interop объявление начинает означать «обязательно».

Названия полей и порядок включения — предмет согласования с сервером; здесь только смысл.

## 5. Интерфейс в коде

- `encrypted.PacketConn`: опция политики — функция `requirePQ(ed25519.PublicKey) bool` (или список ключей с
  обновлением), плюс липкая память внутри пакета.
- arngory/yggdrasil-go: передаёт политику из конфига (`PQRequiredKeys`), выключатель постквантовых сессий целиком
  (на случай отката).
- Ядро (`protocol/yggdrasil`): ключи узлов из профиля (`pq=1`) — в `PQRequiredKeys`.
- niko-server: ключи устройств с `yggdrasil.pq: true` из `users_file`.

## 6. Проверки

- PQ↔PQ: PQ-сессия поднимается, трафик идёт типом 7, классических пакетов после замены нет.
- PQ↔классика (upstream ironwood, yggstack): сессия классическая, без задержки первого пакета.
- Понижение: связь, которая выбрасывает типы 4–7.
  - При «обязательно PQ» соединения нет, классической сессии не возникает.
  - При «по возможности» сессия классическая, ключ не липкий.
  - После PQ-сессии (ключ липкий) выброс PQInfo не ведёт к классике.
- Замена: классика → PQ без потери соединения TCP поверх Yggdrasil.
- Повторный init и повтор PQ init (как `TestRepeatedInitIsAckedAgain`, `TestReplayedInitKeepsKeys`).
- Существующие проверки CI: Yggdrasil probe с yggstack, interop с niko-server, LAN между устройствами.

## 7. Открытые вопросы

- Ротация ML-KEM-ключа процесса: в #48 он один на процесс. Достаточно ли этого для долгоживущего узла, или
  менять раз в сутки с новым PQInfo?
- Липкая память на диске: срок, сброс пользователем, общий ли файл для телефона и компьютера.
- Нужен ли PQ для LAN между устройствами пользователя с первого контакта: устройства одного пользователя могут
  узнать способность друг друга от узла (список устройств).
