# Маршрутизация по приложениям: списки, нода, обновление

Предложение от клиента, 2026-11-16. Повод — замечание владельца: при разбивке по доменам проверка вроде ipinfo.io
видит рассинхрон, и данные к этому моменту уже ушли не туда. Владелец предлагает отдельный репозиторий списков по
приложениям (с их доменами и подсетями) и маршрутизацию на ноде и relay, которую обычный пользователь не перепишет
парой кнопок. Здесь — как это сделать без потери производительности и с какими гарантиями.

Связано: обзор mihomo со стороны сервера (`raycontrol:docs/19-mihomo-review.md`): §3.2 — наборы правил через ноду,
§4.3 — выходы ноды. ID — из [матрицы компьютера](../desktop/REQUIREMENTS.md).

## 1. Почему домены рассыпаются

- Один сервис ходит на десятки имён: свои домены, CDN, аналитика, проверка адреса. Список доменов всегда отстаёт, и
  часть имён уходит другим путём. Сервис видит два адреса: домашний и адрес ноды.
- Сторонние имена общие для многих приложений (SDK аналитики, CDN). Правило по такому имени тянет за собой чужие
  приложения.
- При первом запуске прямое правило пресета ждёт свои списки (`fmt/ConfigBuilder.kt:1121`). Пока их нет, сервисы
  идут через узел, потом прямо: рассинхрон на старте.
- DNS-запросы, которые идут не тем путём, что соединения, выдают те же имена провайдеру.

Вывод: единица маршрута — приложение целиком. Домены и подсети нужны для того же сервиса, когда к нему идёт другое
приложение (браузер, WebView). В браузере полного согласия по доменам не будет никогда; для сервисов, которые
сверяют адрес, честный совет — отдельный браузер, целиком в своём маршруте.

## 2. Репозиторий списков (предложение)

Отдельный репозиторий, например `arngory/niko-routes`. Одна запись — одно приложение или сервис:

```yaml
# apps/ru/sberbank.yaml
name: Сбербанк Онлайн
country: ru
kind: inside-only            # inside-only | blocked | ads
android:
  - package: ru.sberbankmobile
    cert_sha256: [<SHA-256 сертификата подписи>]   # с учётом ротации подписи APK v3
windows: [SberbankOnline.exe]
domains: [sberbank.ru, sber.ru]      # суффиксы
asn: [AS35237]               # только свои AS владельца сервиса
cidr: []                     # явные подсети, если AS нет
cdn: []                      # CDN, на которых живёт сервис: только из закрытого перечня CI
evidence: [ссылка или запись трафика]
```

CI на каждый PR и по расписанию:
- проверяет схему; ищет конфликты (одно имя или подсеть с разными `kind`) и общие имена;
- разворачивает AS в подсети по RouteViews (CC BY 4.0, с атрибуцией, `raycontrol:docs/11-asn-sources.md` §2.7);
- **не пускает подсети CDN и облаков** (Cloudflare, Akamai, Fastly, общие облака): адрес там общий, и подсеть
  потянет чужие сайты. Такие части сервиса ловятся только по имени (сниффинг SNI);
- отвергает слишком широкие подсети (шире /16 для IPv4) и записи без `evidence`;
- не пускает суффиксы, под которыми DNS поддоменов держат третьи лица (общие хостинги, облачные зоны), и ищет
  висячие CNAME на ресурсы, которые можно занять: relay резолвит имена inside-only сам (§5);
- `cdn:` — только провайдеры из закрытого перечня CI, с `evidence` и ревью. Диапазоны этих провайдеров CI собирает
  в отдельные файлы (`cdn-<провайдер>`, только текстовый вид для relay), перечисленные в `manifest.json` под ключом
  списков с `kind: cdn` и без `country`, — нода их не подменит. Запрет подсетей CDN в наборах это не отменяет:
  файлы `kind: cdn` читает только проверка relay «адрес из своего резолва имени этой записи» (§5); сборка
  наборов, nftables ноды и правила клиента их пропускают, и CI проверяет это схемой манифеста;
- собирает `.srs` sing-box: по одному на приложение и по одному на `kind` и страну, плюс `manifest.json` с номером
  версии (только растёт) и для каждого файла — SHA-256, размер, `kind` и `country`. Исключение — `kind: cdn`:
  `.srs` для них нет (только текстовый вид для relay) и `country` нет; схема манифеста описывает это явно. Это `kind` списков
  (inside-only, blocked, ads; country — набор страны; cdn — диапазоны провайдера, только для relay), а не вид набора у ноды (`domain`, `ipcidr` в `19-mihomo-review.md` §3.2): в
  rules-v1 у ноды это поле называется иначе;
- подписывает манифест minisign отдельным ключом списков, не ключом релизов приложения.

Ключей у списков два, как роли content и timestamp в TUF:
- **ключ списков** подписывает манифест с хешами файлов. Работает только при выпуске новой версии, после PR с
  ревью; запуск сборки с ним требует подтверждения человека (окружение GitHub с обязательным одобрением);
- **ключ свежести** подписывает маленький `timestamp.json`: номер и SHA-256 текущего манифеста и `expires`.
  Своего номера у `timestamp.json` нет (или он только метка и не сравнивается): свежесть упорядочивается по номеру
  манифеста. Для одного манифеста из подтверждённых подписей (определение и состояние «ожидает» — §3) берётся
  более поздняя.
  Иначе утёкший ключ подписал бы `timestamp.json` с номером 10^9, и после отзыва ни один честный уже не прошёл бы.
  Плановый запуск CI переподписывает его не реже раза в 7 дней, даже если списки не менялись, поэтому этот ключ
  лежит в секретах CI без участия человека. Это осознанный компромисс: утечка ключа свежести позволяет только
  продлить срок старой версии (заморозить), но не подменить списки. Доступ к секретам — у владельца
  репозитория.
- Нода держит оба файла: `timestamp.json` тянет раз в сутки, а при остатке меньше половины срока — раз в час;
  `manifest.json` — только при новом номере или SHA-256 в `timestamp.json`. В поле `rules` подписки — ссылки на
  оба.
- **Кто меняет ключи — только уровень выше, как в TUF; роль никогда не меняет свой ключ сама:**
  - ключи списков зашиты в сборку клиента и raycontrol, и только там. Смена — выпуском приложения и raycontrol,
    заранее, с двумя ключами на переходный срок;
  - ключи свежести перечислены в `manifest.json`, который подписан ключом списков. `timestamp.json` ключей не
    несёт. Так утёкший ключ свежести не может добавить свой ключ и пережить отзыв: отзыв — новый манифест.
  - Порядок проверки у клиента и ноды: сначала манифест, на который указывает `timestamp.json`, — подпись ключом
    списков и версия не ниже принятой; затем подпись `timestamp.json` ключами свежести из этого манифеста. Так
    новая версия с новым ключом свежести проходит сразу, а клиент, принявший манифест с отзывом, больше не верит
    отозванному ключу. Клиенту, которому нода этот манифест не отдаёт, отозванный ключ ещё может подписывать
    свежесть старой версии — это закрывает еженедельная сверка с GitHub (§3).
- `timestamp.json` плановый запуск коммитит в отдельную ветку `timestamp` без защиты ревью. Это явное исключение из
  правила двух ревью (§6), только для этого файла: целостность списков держит подпись ключа списков, которого у
  CI нет, а не защита ветки. Ключ свежести лежит не в секретах репозитория, а в отдельном окружении GitHub, куда
  допущена только ветка `main`. Окружение ограничивается по веткам, а не по событиям, поэтому задача с ключом
  сама проверяет `github.event_name == 'schedule'`, а `pull_request_target` и `workflow_dispatch` в этом workflow
  запрещены (иначе недоверенный код из PR или любой с правом записи получил бы ключ на `main`). Сильнее — отдельный
  репозиторий только для подписи свежести; решается при сборке CI. `contents: write` у задачи
  — на весь репозиторий, одной веткой его не ограничить: задача может портить ветки и ассеты выпусков. Целостность
  это не ломает (подписи), но остаётся отказ в обслуживании; `main` и теги защищены правилами. Коммит в ветку —
  активность, и GitHub не выключает расписание публичного репозитория после 60 дней тишины. Если расписание всё же встанет, тревогу
  поднимет нода: событие в `rayctl status` за 3 дня до `expires`.

Пресеты стран (D-RULES-05: «Нет, Россия, Китай, Иран», одним выбором — «ок» владельца 2026-11-16) собираются отсюда
же: список приложений и сервисов страны плюс заблокированное. Сторонние списки (runetfreedom, Loyalsoldier,
Chocolate4U) берутся как исходные данные в CI, а не напрямую в клиент.

## 3. Холодный и горячий старт

- **Холодный.** Снимок списков лежит в APK и в установщике компьютера. Последняя проверенная версия — на диске.
  Туннель стартует сразу с полным набором, без окна «списков ещё нет» из §1.
- **Горячий.** Новая версия приходит через ноду: нода держит зеркало, как для APK (app-update-v1). Подписка несёт
  необязательное поле `rules` с хешами (`19-mihomo-review.md` §3.2). Клиент сверяет подпись манифеста и SHA-256,
  подменяет файл атомарно (запись рядом и переименование). Ядро само перечитывает изменённый файл (локальный
  rule-set, `sing-box:route/rule/rule_set_local.go:88-104`; так уже работает `RuleSetFiles.kt`): без перезапуска
  туннеля и без разрыва соединений. Новые соединения идут по новому списку. Сбрасываются только соединения
  приложений, у которых сменился маршрут: иначе одно приложение живёт на двух путях.
- **Откат.** Клиент хранит номер принятой версии отдельно от файлов. С ноды и с GitHub версия ниже принятой не
  ставится. Одно исключение — аварийный снимок: если на диске нет проверенной версии или её подпись или хеш не
  сходятся (чистая установка, порча файла), клиент временно ставит снимок из APK, чтобы не было окна без списков
  (§1). Номер принятой версии при этом не меняется (например, остаётся 50 при снимке 40), клиент сразу
  запрашивает версию не ниже принятой у ноды или GitHub, а до её прихода D-RULES-07 показывает «работает
  аварийный снимок».
- **Заморозка.** Срок годности `expires` — в `timestamp.json` (§2): дата подписи плюс 14 дней, а переподписывается
  он раз в 7 дней, так что при живом репозитории срок не истекает. Нода может раздавать старую, но верно
  подписанную версию, и тогда исправления списков не дойдут. Защита — две независимые проверки GitHub через туннель
  (заголовок `Date` и файлы с GitHub нода подделать не может: TLS до GitHub):
  - **по расписанию, без часов:** раз в 7 дней клиент сам берёт `timestamp.json` с GitHub. Если там версия новее,
    чем раздаёт нода, клиент берёт её (с теми же подписями) и показывает в D-RULES-07, что нода отдаёт старые
    списки. Эта проверка не зависит ни от каких часов и ловит заморозку не позже чем через неделю;
  - **по сроку:** когда по часам устройства срок истёк, клиент тоже идёт на GitHub и сверяет `expires` с его
    `Date`. Истёк и там, новее нет — «списки устарели» с датой. По `Date` не истёк — часы телефона спешат, тревоги
    нет.
  Туннель держит нода, и проверку GitHub она может просто ронять. Поэтому неудача тоже тревога: если еженедельная
  проверка не удалась два раза подряд или с последней удачной прошло больше 14 дней, клиент показывает «списки,
  возможно, устарели: проверить не удалось». Сами списки продолжают работать: выключить их — хуже.

  Предел свежести. `timestamp.json` несёт время подписи и `expires`. Клиент отвергает `timestamp.json`, у
  которого `expires` позже времени подписи больше чем на 14 дней. Время подписи сверяется не с часами телефона, а
  с опорой: последний `Date` от GitHub плюс время, прошедшее с него по монотонным часам (`elapsedRealtime`), или
  `Date`, полученный сейчас прямым походом на GitHub.
  - **Подтверждена** — время подписи сверено с опорой и не впереди неё больше чем на 2 дня (впереди больше — отказ).
  - **Ожидает** — опоры нет: монотонные часы обнуляются при перезагрузке, и до следующей сверки с GitHub сверять не
    с чем. Такой `timestamp.json` хранится как ожидающий для своего манифеста вместе с `elapsedRealtime` момента
    получения; если его время подписи впереди часов устройства больше чем на 2 дня — ещё и немедленный поход на
    GitHub. Когда появится `Date`, время подписи сверяется с опорой, пересчитанной на момент получения (`Date` минус
    прошедшее с получения по монотонным часам): иначе подпись «+10 дней», дождавшись `Date` через неделю,
    обошла бы предел в 2 дня. Если с получения была перезагрузка, ожидающая подпись отбрасывается и
    `timestamp.json` берётся заново. Перезагрузку узнают по номеру загрузки, который хранится рядом с
    `elapsedRealtime`, а не по тому, что `elapsedRealtime` стал меньше: после перезагрузки он может уже обогнать
    сохранённый, и ошибка опоры была бы сколь угодно большой. Номер загрузки: на API 24 и новее —
    `Settings.Global.BOOT_COUNT`, иначе boot_id из `/proc/sys/kernel/random/boot_id`; хранится вместе с типом
    источника. Если тип не совпал или значение не прочиталось, считается, что перезагрузка была (лишний поход на
    GitHub лучше, чем незамеченная перезагрузка). Отказ — только по свежему `Date`.
  - Манифест под ключом списков (версия не ниже принятой) ставится сразу, и при ожидающем `timestamp.json`: его
    содержание подлинно независимо от времени, и отстающие часы не блокируют новые списки. Но свежесть нового
    манифеста не засчитывается, пока его `timestamp.json` не подтверждён; подтверждённый `timestamp.json` старого
    манифеста свежесть нового не продлевает. Пока свежесть не подтверждена, D-RULES-07 показывает «не
    подтверждено»; если нода роняет GitHub, тревога «проверить не удалось» горит, как ниже, не позже чем через 14
    дней.
  - Время подписи клиент не считает монотонным (не требует, чтобы оно только росло): иначе однажды принятая
    подпись «из 2099 года» заблокировала бы все честные обновления после неё.

  Что это даёт, честно: предел мешает одному долгому сроку без живого канала. Нода с утёкшим ключом свежести,
  которая переподписывает свежесть каждый день и роняет GitHub, укладывается в любые пределы — её ловит только
  еженедельная сверка с GitHub, и тревога «проверить не удалось» загорается не позже чем через 14 дней.

  Время ноды (`issued` в подписанном payload, subscription-v1 §3) нигде не хранится и ничего не откладывает:
  замораживающая нода подпишет любое время, а нода с часами в 2099 году не должна навсегда зажечь тревогу. Если
  `issued` позже `expires`, это только повод сходить на GitHub раньше. Решает всегда `Date` от GitHub.

## 4. Производительность

- **Приложение.** Пакеты переводятся в UID один раз, при сборке конфига (`fmt/ConfigBuilder.kt:1128-1144`). Ядро
  сравнивает UID соединения с набором чисел. Владельца соединения ядро и сейчас ищет, как только есть хоть одно
  правило по приложениям: на Android это один вызов системы на новое соединение, не на пакет.
- **Имя.** Суффиксы в `.srs` лежат в succinct-структуре (`sagernet/sing:common/domain/set.go`). Поиск зависит от
  длины имени, а не от размера списка.
- **Подсети.** Отсортированные диапазоны, двоичный поиск.
- **Память.** Списки приложений — килобайты. Они могут заменить большие geosite и geoip там, где те нужны только
  ради пресета: это прямо в задаче про RAM (#124).
- **Нода.** Подсети — наборы nftables в ядре. Обновление — одна транзакция `nft`, без перезапуска процессов, как
  у egress-policy-v1 (1–2 с). Имена — в процессах: у Xray правило `domain`, у naive имя из CONNECT, у Hysteria2 —
  новое (`19-mihomo-review.md` §4.3).

## 5. Кто что решает

Порядок правил на клиенте:
1. Обязательные правила от ноды (`enforce`): `block`, `node`, `relay`, `direct` — по порядку, выше всего. Видны с
   замком «Задано подпиской», пользователь их не меняет.
2. Свои правила пользователя по приложениям. Приложение с таким правилом выпадает из списков (правило 3).
3. Приложения из включённых списков — целиком одним путём.
4. Остальные свои правила пользователя.
5. Имена и подсети сервисов из списков — для остальных приложений.
6. Пресет страны.
7. Остальное — через узел.

DNS идёт тем же путём, что и соединение: правила DNS строятся из тех же списков.

**Модель доверия (решение владельца 2026-11-16).** Клиент по архитектуре недоверенный: цель ноды — hardening, и
маршрутизацию, нужную ноде, обычный пользователь парой кнопок не перепишет. Поэтому у администратора все
возможности, включая `direct`: нода может отправить выбранные наборы мимо туннеля. Цена записана открыто и
объясняется в справке приложения: администратор подписки (или тот, кто взломал ноду) может отправить выбранные
сайты напрямую и открыть им домашний адрес пользователя; доверяете подписке — доверяете её администратору; нужна
независимость — свой raycontrol и Niko. Клиент показывает каждое правило ноды с замком и действием, включая
«напрямую», — это прозрачность, а не защита. Так же и `relay` и `node` от ноды стоят выше своих правил
пользователя: приложение, которое пользователь сам отправил через узел, чтобы скрыть его от своей страны, нода
может перевести на relay в этой стране — его оператор и провайдер страны увидят назначения. Это тоже цена прав
администратора, и справка говорит о ней рядом с «напрямую». На ноде `direct` включается только явно, с
подтверждением: `rayctl` пишет, что это значит, ставит строку аудита (только тег набора), а `rayctl status`
перечисляет действующие правила `direct`; та же цена — в гайде и шпаргалке raycontrol. Прежнее предложение клиента («нода не может слать мимо туннеля»)
владелец отклонил.

Обязательные правила приходят в подписке полем `enforce` (черновик сервера, окончательно — в его спеке rules-v1):
по порядку, все выше правил пользователя; действия `block`, `node`, `relay`, `direct`; неизвестное действие клиент
пропускает.

Что клиент проверяет в `enforce`:
- `block`, `node` и `direct` применяются к любому набору, в том числе к своим наборам ноды, кроме `kind: cdn`:
  правило `enforce` на такой файл клиент отбрасывает с предупреждением (это не набор правил, а диапазоны для
  проверки на relay, и `.srs` у него нет).
- `relay` — только к набору с `kind: inside-only` из манифеста, подписанного ключом списков. Набор из `enforce`
  клиент находит по имени файла в своём принятом манифесте (клиент может быть на версию впереди ноды: по хешу
  наборы ноды тогда не нашлись бы, и правило `relay` выпало бы — банк пошёл бы по правилам пользователя, возможно
  за границу). Файл и `kind` берутся только из манифеста клиента, не из полей ноды. Если набор не найден или его
  файла нет, правило `relay` не выпадает, а работает по своему `fallback` (по умолчанию отказ): сейчас
  `ConfigBuilder` молча пропускает правило, чей файл ещё не скачан, — для `enforce` так нельзя. Правило `relay` на другой
  набор (например, на заблокированное) или на набор самой ноды клиент отбрасывает и показывает предупреждение:
  relay в стране пользователя не должен становиться прокси для того, что от этой страны прячут; выход relay
  отвергнет такое и сам (ниже).
- Вход relay не отвечает: по умолчанию правило отказывает (`"fallback": "none"`), а не уходит через узел. Сервисы
  inside-only смотрят на страну адреса, и вход в банк с иностранного адреса — это риск блокировки счёта, хуже
  отказа; так же решил владелец 2026-11-14 для недоступного выхода (`19-mihomo-review.md`, решения владельца,
  п. 3). `"fallback": "node"` администратор ставит сам на наборы, где иностранный адрес безвреден.
  «Почему не работает» в обоих случаях пишет «вход relay не отвечает», при `node` — ещё «идёт через узел».
- Набор из `rules` и набор пресета совпадают по SHA-256, а не по тегу: файл с тем же хешем не качается второй
  раз и берётся из `rules`.

```json
"enforce": [
  {"set": "ads", "action": "block"},
  {"set": "ru-blocked", "action": "node"},
  {"set": "ru-inside-only", "action": "relay", "relay": "<id из relays[]>"}
]
```

Выход сервисов «только изнутри» со своего адреса в стране пользователя (ответ сервера 2026-11-16):
- **Сам relay делить не может.** Relay — L4: он пересылает зашифрованный трафик на выход (DNAT), REALITY, naive и
  Hysteria2 сквозные до выхода (relay-v1). Ни имени, ни адреса назначения relay не видит. Расшифровывать всё на
  хосте в стране пользователя сервер отвергает.
- **Вариант Б (рекомендация сервера и клиента): свой вход на relay.** На relay свой небольшой data plane —
  naive из `rayd`, с учётными данными только этого relay (их утечка не даёт данных выхода). В подписке у relay
  свой профиль (`relays[].local`). `enforce` с действием `relay` ведёт туда приложения inside-only целиком, а их
  имена и подсети — для остальных приложений. Это туннель, а не «напрямую»: домашний адрес скрыт. Сервис видит один
  адрес на всех своих именах, без петли через границу. Цена: процесс и учётные данные на relay, CPU на TLS; relay
  видит назначения только трафика inside-only — то, что провайдер увидел бы при «напрямую».
- **Вариант А: решает выход, выпускает relay.** Выход сам относит соединение к inside-only и отдаёт его relay
  (выход `relay:<имя>`, `19-mihomo-review.md` §4.3). Клиенту менять нечего, но выход не знает приложения, только
  имена и адреса: рассинхрон на именах вне списка остаётся. Трафик дважды пересекает границу: плюс два
  международных RTT и двойной трафик.
- Общие риски: адрес relay — адрес хостинга, банки иногда такие не пускают, проверять по каждому сервису;
  оператор relay становится в своей стране прокси для чужого трафика — юридический вопрос владельца; нагрузка
  (банки мало, видео много).

**Relay как выходной хоп** (владелец 2026-11-16: «да, но трижды подумать»; можно ли relay выходить в интернет
как хоп со своей маршрутизацией или собирать всё на клиенте, при том что каждый выход фильтрует и построен по
zero trust). Развитие варианта Б, согласовано с сервером (его спека relay-entry-v1):

1. **Клиент решает, хоп проверяет.** Клиент знает приложение, поэтому выбирает хоп он: «через узел», «через relay
   в стране» или «через relay к узлу» (как сейчас в relay-v1). Хоп не верит выбору на слово: что выпустить, relay
   решает по тому, подтверждено ли соединение (app-attest, §5а), и по наборам под ключом списков. Ключа списков у
   ноды нет, поэтому даже взломанная нода не расширит разрешённое relay.
2. **Приложение целиком — по умолчанию** (решение владельца 2026-11-16): приложение идёт одним путём со всеми
   своими обращениями, и внутри страны, и за границу. Деление «своё и отечественное — своим путём, иностранное —
   через узел» по умолчанию не строим (дырявая многоножка); оно — опция администратора, «адаптивный» режим.
   Два вида соединений на входе relay, и ядро relay различает их не общим набором, а по UID владельца сокета
   (`meta skuid`): сокеты подтверждённых соединений создаёт маленький помощник `rayd relay-entry-sock` под вторым
   UID и передаёт входу (метку `SO_MARK` ставить нельзя: для неё нужен `CAP_NET_ADMIN`, а с ним процесс, смотрящий
   в интернет, переписал бы nftables):
   - **Подтверждённое** (подписано аттестованным ключом и несёт тег inside-only): relay выпускает приложение
     целиком, TCP и UDP, по любому адресу. Остаётся политика выхода, как у ноды: частные сети, сам relay и выход
     закрыты, SMTP и BitTorrent режутся. Проверка имени (п. 3) здесь не нужна: разрешено любое назначение.
     Заблокированное в стране через relay не откроется — у relay тот же провайдер страны, — как и при «напрямую».
     Поэтому суперприложения с браузером или видео внутри (WebView) попадают в inside-only только после
     отдельного ревью списка: весь их трафик пойдёт через relay в стране.
   - **Неподтверждённое** (компьютер, рут, протокол без app-attest): relay не знает приложения и выпускает только
     назначения из наборов inside-only и адреса своей страны (набор страны собирает CI списков из делегирований
     RIR и IPinfo Lite, подписан ключом списков) — иначе relay стал бы прокси для чего угодно. Иностранное relay
     отвергает отличимым ответом: naive `403` с `Niko-Refused: policy` и `Niko-Lists-Version`, без тела. По
     умолчанию это отказ по `fallback` набора (приложение целиком, без деления). Только в адаптивном режиме
     клиент ведёт через узел назначения, которых нет ни в одном наборе inside-only клиента, и показывает их в
     «Проверке маршрута» как материал для списка; назначение из набора и там — отказ по `fallback` (relay на
     старой версии или взломан).
3. **Проверка имени — для неподтверждённых** (дыра F1, найдена сервером). Одного имени в CONNECT мало: клиент мог
   бы открыть CONNECT на разрешённое имя на общем CDN и внутри TLS послать другой SNI. Поэтому relay смотрит
   первые байты потока: SNI в ClientHello и Host в HTTP должны совпасть с именем CONNECT или попасть под суффикс
   inside-only (или адрес назначения — в набор страны); ECH с чужим внешним именем — отказ; поток не TLS и не HTTP
   — только если адрес в подсетях inside-only или в наборе страны. Фронтинг внутри TLS (`:authority` не равен SNI)
   так не ловится, и CDN закрыли его далеко не все: Google и CloudFront — в 2018, Azure — в 2022–2024, Fastly — с
   2024-02-27, а исследование WWW '24 нашло рабочий фронтинг на 22 CDN из 30, среди них Akamai. Держит другое:
   ядро relay выпускает неподтверждённые соединения только в набор страны и подсети списков, подсетей CDN там нет
   (правило CI), поэтому имя на иностранном CDN дозвониться не может. Исключение — имена inside-only (банк на
   CDN или в облаке): relay резолвит такое имя сам и открывает полученные адреса только для этого соединения, и
   только если адрес попал в AS или подсети этой записи либо в явный список CDN записи (`cdn:`, диапазоны
   провайдеров CI публикует отдельно); к таким адресам действует та же политика выхода, что у ноды (частные сети,
   сам relay и выход закрыты). Администратор может исключение выключить. Остаток — фронтинг на этих адресах и
   захват висячего поддомена (имя под суффиксом записи указывает на ресурс, который занял чужой) — записан в
   модели угроз сервера; против второго CI списков проверяет суффиксы (ниже, §2).
   Фронтинг через внутренний CDN обхода не добавляет: тот доступен изнутри и без relay.
4. **Страна relay** (дыра F3): не из снимка ноды — взломанная нода поставила бы «us» и сделала relay открытым
   прокси в США. Relay сам сверяет свой публичный адрес с подписанным набором страны и не принимает страну, в
   которую его адрес не входит.
5. **Что нужно от клиента.**
   - На relay — CONNECT по имени, без своего резолва (FakeIP или сниффинг; имена резолвит relay в стране, то же
     видит провайдер). Нет имени (FakeIP выключен, сниффинг не дал) — CONNECT по адресу на вход, а не через узел:
     иначе банк ушёл бы за границу при `fallback: none`.
   - **UoT и ICMP на relay не идут никогда**: вход v1 их не принимает (`403`), у outbound relay их нет. UDP
     приложения на relay — только connect-udp, ICMP — через узел или отказ по `fallback`.
   - UDP. Подтверждённое приложение шлёт на relay весь свой UDP. Неподтверждённое — только к адресам из наборов
     или к именам inside-only (с FakeIP в датаграммах имена); остальной его UDP по умолчанию — отказ по
     `fallback`, через узел — только в адаптивном режиме. У outbound relay нет UoT и проверки UDP-зонда.
   - connect-udp: запрос `/.well-known/masque/udp/*/*/` — один сокет на много назначений (адрес в каждой
     датаграмме), поэтому вход отвечает `200` сразу и не ждёт первой датаграммы, а недопустимые датаграммы
     отбрасывает молча, со счётом. Отказ по первой датаграмме убил бы весь сокет, а нынешний клиент любой `403` на
     connect-udp читает как «узел не умеет датаграммы» и переводит весь UDP этого outbound (этого relay) в этой
     сети на UoT; узел это не затрагивает.
   - **План для клиента, сейчас этого нет:** `403` с `Niko-Refused` на connect-udp — `policy` (старый relay) или
     `attest` (строгий режим app-attest отказывает по классу приложения целому сокету) — отказ только этому сокету,
     отдельной веткой, без счёта в отказах подряд (сейчас `datagramRefusedOnce` в
     `sing-box:protocol/naive/datagram_neko.go` видит только статус и берёт лишь 429 и 503, а три таких подряд
     тоже переводят на UoT). Для outbound relay UoT выключен вовсе: вход v1 UoT не принимает (`403`), так что
     connect-udp, который не работает на relay, — отказ UDP по `fallback` набора, а не переход на UoT.
   - TLS входа. Клиент идёт на relay по адресу, а пины ключа в Chromium (и в cronet-go: `naive_client.go`
     отказывает пинам для адреса) работают только для имён. Поэтому у relay — свой сертификат как
     **единственный доверенный корень** этого outbound. В `relays[].local` — два сертификата: текущий и запасной
     (ключ сгенерирован заранее и хранится отдельно); следующий публикуется заранее, до смены. Плановая смена
     ключа (переустановка relay): сначала новый сертификат раздаётся в снимке и подписке, потом relay
     переключается. При потере или утечке ключа так нельзя: старый сертификат оставался бы доверенным, пока новый
     расходится. Тогда relay сразу переходит на запасной, который уже у клиентов, утёкший убирается, и раздаётся
     новый запасной.
   - **Блокирующее условие:** сейчас свой корень в cronet-go ставится только через тестовый верификатор
     (`EngineSetMockCertVerifierForTesting`, `cronet-go/engine_purego.go`). Сервер добавляет нормальный API —
     `EngineParams.ExactServerCertificates` (DER): движок принимает сервер, только если листовой сертификат равен
     одному из заданных, без цепочки и проверки имени, для h2 и h3, а системные корни и пины этого движка не
     используются (патч naiveproxy и cronet-go, сборка в CI). Пока его нет, outbound relay в клиенте не включается.
6. **Zero trust между хопами:**
   - у каждого хопа свои учётные данные, выведенные только для него: утечка с relay не даёт ничего на выходе и на
     других relay;
   - клиент проверяет каждый хоп: узел — по пинам, как сейчас; relay — по собственному корню как единственному
     доверенному (п. 5);
   - путь «через relay к узлу» остаётся сквозным до выхода (L4 на relay): relay не читает трафик, идущий за
     границу;
   - конфиг relay подписан нодой, наборы — ключом списков; отзыв пользователя на ноде доходит до relay;
   - у выхода relay та же политика, что у ноды: частные сети и сама нода закрыты, SMTP и BitTorrent режутся
     (egress-policy-v1).
7. **Что это даёт против взлома и чего стоит:**
   - взломанный (неподтверждённый) клиент получает от relay только внутренние сервисы своей страны, которые и так
     открыты; подтверждённое приложение relay выпускает и за границу — но только приложение из inside-only,
     проверенное ключом устройства;
   - взломанная нода не расширит наборы, которые relay выпускает неподтверждённым (они под ключом списков), но по
     модели доверия (выше) может послать выбранные наборы напрямую — это цена прав администратора;
   - взломанный relay видит назначения трафика, который через него идёт (inside-only приложения целиком), и не
     может выдать себя за выход;
   - юридически relay выходит в интернет от имени приложений inside-only, в том числе за границу: оператор relay
     в стране становится прокси для их трафика. Заблокированное через него не открывается. Владелец этот риск
     принял (2026-11-16, «делаем»), «приложение целиком» на relay — по умолчанию.
8. **Свои правила пользователя** выбирают хоп в пределах того, что хоп разрешает. Клиент предлагает «через relay
   в стране» только для наборов inside-only, чтобы не было непонятных отказов.
9. **Цена:** TLS на relay для всего трафика приложений inside-only (банки мало, видео и суперприложения много —
   relay брать под это); проверка по набору — микросекунды (nftables, succinct-набор).

Ещё на сервере:
- **Выход ноды для пользователя** (`rayctl user egress`, `19-mihomo-review.md` §4.3): постоянный адрес выхода,
  чтобы сайты, которые следят за адресом сессии, не разлогинивали.

Чего не сделать ни клиенту, ни серверу: приложение на телефоне всё равно видит, что VPN включён (интерфейс
`tun0`), даже если его трафик исключён из туннеля. Android не даёт VPN-приложению это скрыть. Без VPN совсем —
только режим «Прокси».

## 5а. Приложение на стороне сервера (app-attest, предложение)

Сейчас нода и relay видят пользователя и назначение, но не приложение: его знает только телефон. Владелец
(2026-11-16): доверие — краеугольный камень, клиент может навредить серверу, сервер — клиенту; либо сервер знает
приложение как штатная функция, либо маршрутизация по приложениям дырявая по природе. Схема согласована с сервером
(его спека app-attest-v1 — следующая); администратор включает её сам, по умолчанию выключена.

1. **Регистрация ключа — раз в сутки, при выборке подписки** (аппаратная аттестация ключа Android, без Google
   Play). На каждую аттестацию Niko создаёт **новый** ключ в TEE с вызовом ноды (`setAttestationChallenge`), а
   старый удаляет: уровни патчей, состояние загрузки и вызов записываются в сертификат один раз, при создании ключа,
   — со старым ключом обновлённое устройство показывало бы старые патчи, а взломанное — состояние до взлома.
   Цепочка идёт к корням аттестации Google (в `rayd` зашиты оба: старый RSA и новый ECDSA) и несёт пакет и SHA-256
   подписи приложения (`attestationApplicationId` — настоящий Niko с нашей подписью), `rootOfTrust` и уровни
   патчей. Выход сверяет `attestationChallenge` в листовом сертификате, проверяет список отзыва Google (берёт раз в
   сутки; старше 7 дней — событие) и свежие `osPatchLevel` и `vendorPatchLevel` (по умолчанию не старше 12
   месяцев, администратор меняет). Хранит открытый ключ и вердикт устройства (не цепочку) до следующей аттестации,
   не дольше 7 дней. GrapheneOS проходит со своим ключом проверенной загрузки (нода может разрешить его отдельно).
   Ключ — в TEE: StrongBox подписывает сотнями миллисекунд; нода примет оба, в вердикте видно, откуда ключ.
2. **Доказательство — на каждое туннельное соединение** (ключ TEE не вынуть даже рутом, в отличие от токена в
   памяти приложения; токен на предъявителя поэтому не берём). В новом туннельном соединении naive (h2 или h3)
   клиент первым открывает служебный поток `CONNECT attest.niko.arpa:0`; нода отвечает `200` с
   `Niko-Attest-Nonce` (32 байта) и запоминает nonce за этим соединением; клиент пишет в поток подпись
   аттестованным ключом над `"app-attest-v1" ‖ 0x00 ‖ nonce ‖ node_id` и отпечаток ключа; нода сверяет с
   зарегистрированным ключом и отвечает байтом статуса. Повтор невозможен: nonce свежий и живёт только в своём
   соединении, а `node_id` в подписи не даёт relay предъявить её выходу. Цена — один RTT в начале соединения;
   потоки с тегом клиент шлёт после ответа, иначе первый поток банка ушёл бы «неизвестным» и получил отказ на
   входе relay. relay получает в снимке выхода открытые ключи подтверждённых устройств и проверяет подпись сам.
   Позже подпись можно перевести на TLS exporter (Chromium его умеет): без состояния у ноды и без лишнего RTT.
3. **Тег — только настоящему приложению.** Подтверждённое приложение inside-only relay выпускает целиком, поэтому
   приложение с чужим именем пакета (тот же `ru.sberbankmobile` из APK со стороны) тега получить не должно: иначе
   relay стал бы открытым прокси для этого пользователя. Запись в списке несёт пакет и SHA-256 сертификатов
   подписи (`cert_sha256`, CI требует их); Niko ставит тег, только если подпись установленного пакета совпадает
   (`PackageManager`, `GET_SIGNING_CERTIFICATES`, с учётом ротации подписи APK v3). Поэтому app-attest требует
   Android 9 (API 28) и новее: ниже нет ни `GET_SIGNING_CERTIFICATES`, ни истории подписей, и такой телефон —
   неподтверждённый (`minSdk` приложения — 23). Для Windows по имени программы
   такой проверки нет, но компьютер и так неподтверждённый.
4. **Что сообщает клиент — класс, а не имя приложения.** Политике ноды нужен класс («приложение из набора
   `ru-inside-only`»), а не «у человека Сбербанк». Клиент шлёт тег набора из подписанного манифеста, в котором
   нашлось приложение, и версию манифеста. Чёрный список ноды приходит клиенту набором со своим тегом и считается
   включённым: подлинный Niko шлёт его тег. Правило на конкретную запись — отдельное поле позже, если понадобится.
5. **Только naive.** У Hysteria2 и VLESS/REALITY нет места для метаданных на соединение, а учётные данные «по
   классу» скопирует кто угодно. Эти протоколы — класс «неподтверждённый». Вход relay и так только naive.
6. **Что нода делает с тегом:**
   - на выходе: соединение с тегом inside-only, для которого в `enforce` стоит `relay`, получает
     `403 Niko-Refused: policy` — нода не везёт банк за границу, если подлинный клиент ошибся. Подменённый клиент
     аттестацию не пройдёт и тег не пошлёт: от него это защищает, только если администратор не пускает
     неподтверждённых на выход или ставит им режим «строго»;
   - вход relay у подтверждённых принимает только теги inside-only и выпускает такое приложение целиком, по любому
     адресу (п. 2 «Relay как выходной хоп»); у неподтверждённых — как в relay-entry-v1
     (наборы и страна), если администратор их пускает;
   - тег `Niko-App-Set` (с `Niko-Lists-Version`) учитывается только в подтверждённом соединении, иначе —
     «неизвестно»;
   - режимы администратора: выключено (по умолчанию); «учитывать» — чёрный список и `enforce` по тегам, неизвестное
     пропускается; «строго» — только разрешённые теги, неизвестное — отказ; отдельно — «только цепочки RKP».
     Чёрный список держит лишь подлинных клиентов, неподтверждённый умолчит;
   - `direct` нода не проверит никогда: такой трафик к ней не приходит. Справка говорит это прямо.
7. **Пределы, честно:**
   - пакет в аттестации вписывает keystore ОС, а не TEE: TEE ручается за загрузку и уровни патчей. Эксплойт ядра на
     устройстве с заблокированным загрузчиком подменит пакет — поэтому нужен свежий уровень патчей;
   - рут, разблокированный загрузчик, прошивки без своего ключа — аттестацию не проходят: клиент
     «неподтверждённый», администратор решает, давать ли ему маршруты по приложениям;
   - компьютер (Windows) так не доказать: TPM подтверждает ключ, но не то, что процесс Niko не подменён;
   - пока устройство подтверждено (до 7 дней), взломавший его во время работы может подписывать вызовы ключом
     TEE, но не вынести ключ; следующая регистрация такой телефон отсеет по `rootOfTrust` и патчам;
   - аттестацию обходят утёкшими ключами производителей; список отзыва ловит известные, не все. Это планка, а не
     доказательство.
8. **Приватность:** тег уходит только для приложений из включённых списков и чёрного списка ноды (остальные —
   «неизвестно») и в журналы не пишется — журналы доступа на ноде выключены (решение D-12,
   `raycontrol:docs/08-decisions.md`), только счётчики по наборам. Промежуточный сертификат RKP бывает уникален для
   устройства несколько дней: выход цепочку не хранит, только вердикт и время.
9. **Чего это не меняет:** содержимое TLS нода не читает — для этого телефон должен доверять её корневому
   сертификату. Нода не может прислать клиенту свой корень: свой корневой сертификат (D-RULES-04) добавляет только
   пользователь, вручную и с предупреждением.

## 6. Безопасность и качество

- Две подписи на пути: ключ списков на манифесте и подписанный ответ ноды с хешами. Ключ списков вшит в клиент.
- Номер версии только растёт, а у `timestamp.json` есть срок годности не длиннее 14 дней (§2, §3). Нода не может
  откатить списки; заморозку ловит еженедельная сверка с GitHub, и не позже чем через 14 дней горит тревога (§3).
- `relay` из `enforce` — только для наборов `inside-only` из подписанного манифеста (§5). Выход relay выпускает
  подтверждённое приложение inside-only целиком, а неподтверждённым — только эти наборы и адреса своей страны;
  заблокированное в стране через relay не открывается.
- `direct` из `enforce` — право администратора (решение владельца, §5); клиент показывает такие правила открыто,
  справка объясняет цену.
- `relay` и `node` из `enforce` перекрывают свои правила пользователя, в том числе приложение, которое пользователь
  сам отправил через узел (§5): справка говорит и об этом.
- Действия в списках — только `inside-only` (напрямую или вход relay), `blocked` (через узел), `ads` (блок).
  Списки не называют исходящих и не вводят новых.
- Каждое изменение списков — PR с `evidence`, ревью двумя людьми, воспроизводимая сборка `.srs`. Исключение —
  только `timestamp.json` в ветке `timestamp` (§2).
- Ключи меняет только уровень выше (§2): роль не может сама себе добавить ключ.
- Клиент показывает версию и дату списков и в «Проверке маршрута» — путь каждого имени сервиса: видно, где
  сервис расходится.

## 7. Решения владельца

1. Репозиторий: `arngory/niko-routes`, публичный — «ок» владельца 2026-11-16. Списки ведём мы; основной ключ
   подписи добавляет владелец. Входящие PR принимаются, но только в разрешённые места (README репозитория,
   «Contributing»).
2. Обязательные правила ноды — решение владельца 2026-11-16: у администратора все возможности, включая
   `direct`; клиент недоверенный, цена объясняется в справке (§5).
3. Свой выход в стране пользователя — «да» владельца 2026-11-16 с условием трижды продумать: relay как выходной хоп
   с фильтрацией и zero trust, согласовано с сервером (его спека relay-entry-v1, §5).
4. Приложение — одним путём целиком по умолчанию (владелец 2026-11-16); деление «своё — своим путём, иностранное —
   через узел» — только адаптивный режим администратора. На relay подтверждённое приложение inside-only выходит
   целиком, неподтверждённому — наборы и адреса страны, остальное — отказ по `fallback`. Риск оператора relay
   владелец принял («делаем», 2026-11-16).
