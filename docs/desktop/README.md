# Niko для компьютера: дизайн и устройство

Рабочий документ этапа 2 десктопа. Требования к каждому элементу экрана, от интерфейса до ядра, ведутся в
[REQUIREMENTS.md](REQUIREMENTS.md); здесь — как мы работаем над дизайном, как устроено приложение и что ещё решить.

## Стек (решение владельца)

- **Интерфейс:** Dart + Flutter (Windows сначала, Linux потом). Electron не берём. Код — в [`desktop/`](../../desktop/README.md).
  Material не используется: компоненты дизайн-системы свои, на слое `widgets`; цвета, размеры и стили текста
  генерируются из `shared/tokens.json`.
- **Демон:** `boxdd` из нашего форка ядра (служба Windows, gRPC). Сборка под Windows уже в CI (`desktop.yml`):
  `boxdd.exe`, `sing-box.exe`, `libcronet.dll`. naive под Windows проходит тесты.
- **Логика Niko:** Go. Пакеты `libcore/raysub`, `rayapi`, `rayprobe`, `probe`, `dnsprobe`, `stun`, `minisign` уже
  собираются и проходят тесты под Windows в том же CI.

## Как работаем над дизайном (Claude Design)

1. **Площадка и источник правды — Claude Design** в аккаунте владельца: холст с экранами и дизайн-система «Niko» (на
   основе mdll владельца: цвета обеих тем, шрифты, отступы, компоненты `m-*` и свои `n-*`). Одна система для телефона и
   компьютера. Холст и система приватны; ссылки на них в репозиторий не кладём, их даёт владелец. Здесь живут матрица
   требований, решения и [опись всех функций против дизайна](../design/FUNCTIONS.md): вся функциональность
   закладывается в дизайн сразу (решение владельца).
2. **Ревью.** Сессия разработки открывает холст по ссылке владельца и читает экраны сама: они живой HTML, выгрузки не
   нужны. Экраны сверяются с матрицей. Ответ — список правок по ID; правки на самом холсте — в копии артборда с
   припиской «— правки разработки», экраны дизайна разработка не меняет.
3. **Варианты.** Сравнение идёт на одном холсте: вариант в столбце, экран в строке, одинаковые ID у обоих. Сейчас там
   A — третий раунд из pen.dev (картинки его выгрузки) и B — те же экраны на дизайн-системе mdll владельца.
4. **Имена = ID требований.** ID — в схеме дизайн-сессии: `D-<ЭКРАН>-<номер>`, например `D-MAIN-12 · Пинг`,
   `D-ADD-06 · PIN приглашения`. ID стоит в названии артборда и элемента, и тот же ID — в комментарии в коде Flutter
   (`// D-MAIN-12`). Матрица отмечает для каждого ID, совпадает ли макет с данными. Так видно, что нарисовано, что
   сделано и чего нет. Позже это сможет проверять скрипт в CI.
5. **Раунды:**
   1. **Каркасы** всех экранов из матрицы, чёрно-белые, без украшений.
   2. **Состояния:** первый запуск, подключение, ошибка, нет сети, подписка истекает, трафик исчерпан, служба не
      установлена.
   3. **Токены:** цвета, шрифты, отступы в дизайн-системе (её `tokens.json`, темы light/dark). Они один к одному
      переходят в `ThemeData` Flutter.
   4. **Компоненты:** кнопка питания, строка способа подключения, карточка узла, переключатель пресета, строка журнала.
      В дизайн-системе это компоненты (у mdll — классы `m-*`), во Flutter — виджеты с теми же именами.
   5. **Тексты** на русском и английском. Ошибки называют причину и следующее действие.

   Раунды 1–3 сделаны в pen.dev (до 2026-11-16); его файлы `.pen` в репозиторий не клали: в них привязка к облаку
   pen.dev.
6. **Правила для всех экранов:**
   - Цвет — не единственный признак: у пинга есть число, у ошибки есть значок и текст.
   - IP выхода не запрашивается сам. Только по кнопке, с предупреждением, что запрос уходит на внешний сервис
     (решение владельца).
   - Проверки сервисов тоже только по кнопке.
   - Способы подключения называются как есть: naive, Hysteria2, REALITY, DNS-туннель. Запрет mdll на названия
     протоколов был для его собственного транспорта и к Niko не относится (решение владельца).
   - Технические величины — латиницей, как в журнале ядра: `38 ms`, `4.2 MB/s`, `TCP 443`, `UDP: QUIC`. Что они
     значат, объясняет FAQ (справка) приложения, а не подписи на экране (решение владельца).
   - Разделы в шапке — только текстом, без подчёркиваний и полос (решение владельца). Выбранный раздел отличается и
     начертанием, не одним цветом: полужирный цветом основного текста, остальные — обычные вторичным (у mdll эти два
     цвета различаются меньше 3:1). Наведение — только цвет основного текста. Выбранный раздел помечен и для экранного
     диктора (`Semantics(selected: true)` во Flutter).
   - Подписи короткие, без пояснений «как это работает»: что объяснять — в справку. Действие, у которого есть ясный
     значок (обновить, скопировать, поделиться, удалить, добавить), — кнопкой-значком с подписью для диктора; словом —
     только где без него не понять (подтверждения, «Установить», «Сбросить…», «Закрыть все»). Лишних элементов не
     добавлять (решение владельца).

## Как устроено приложение

```
<install>\sing-box.exe (Flutter)
   │ named pipe
   ▼
<install>\resources\daemon\sing-box-daemon.exe worker      ← тот же файл, что и демон, подкоманда worker
   │ named pipe, проверка подписи и родителя
   ▼
<install>\resources\daemon\sing-box-daemon.exe (служба)
   ├─ boxdd: ядро, TUN, системный прокси
   └─ NikoService: профили, подписки, raycontrol, сборка конфига
```

- **Как `boxdd` проверяет клиента на Windows** (`experimental/boxdd/peer_windows.go`, `security_windows.go`):
  - Имена и каталоги заданы в коде. Демон — `sing-box-daemon.exe` в `<install>\resources\daemon\`, приложение —
    `sing-box.exe` в `<install>\`. Без `--listen` демон в другом месте не стартует; с `--listen` (режим разработки, см. ниже)
    проверки раскладки и подписи пропускаются.
  - Worker — это тот же исполняемый файл, что и демон, запущенный с подкомандой `worker`. Отдельную программу демон не
    примет.
  - Родитель worker'а должен быть установленным приложением.
  - Приложение, worker и демон подписаны одним сертификатом Authenticode.
  - Worker сам обслуживает `ApplicationService` и передаёт приложению проверенное соединение с демоном
    (`--daemon-relay-socket`).
- **Имена — задача этапа 3.** Когда `boxdd` выносится в пакет, либо параметризуем имена и раскладку в форке, либо
  называем файлы так, как ждёт `boxdd`. Встроенное обновление (`update_windows.go`) тоже ждёт своё: установщик NSIS с
  именем продукта `sing-box`. `desktop.yml` сейчас кладёт ядро как `sing-box.exe`, а это имя `boxdd` ждёт у
  приложения. Ядро из CI нужно переименовать, а `boxdd.exe` — назвать как демон.
- **Почему Go для логики.** Всё, что должно работать в фоне без окна, живёт в службе: сторож, обновление подписок,
  адаптивность канала, отчёты. Окно Flutter может быть закрыто. Сейчас эта логика в Kotlin (около 6000 строк в
  `io.niko.raycontrol`) и в парсерах ссылок (около 7000 строк в `io.niko.fmt`). Переносим её в Go один раз; потом
  Android переходит на ту же Go-версию блок за блоком.
- **Как проверяем перенос.** Golden-тесты: один набор входов (ссылки, подписки, ответы узла) прогоняется через Kotlin и
  через Go. Сравниваются получившиеся профили и JSON конфига ядра. Пока Go не совпадает с Kotlin, Android остаётся на
  Kotlin.
- **Новый API.** `NikoService`: свой proto рядом с `boxdd`. `boxdd` сейчас `package main`, поэтому его службы нужно
  вынести в импортируемый пакет форка. Тогда `libcore/cmd/nikod` соберёт `boxdd` и `NikoService` в один бинарник
  демона (он же worker). Имена и раскладка — см. выше.

## Что решить

1. **Сертификат подписи Windows — решено: свой самоподписанный ключ проекта**, без покупки (владелец, 2026-11-16).
   `boxdd` принимает его как есть (`experimental/boxdd/authenticode_windows.go`):
   - нужен EKU codeSigning;
   - проверяются самоподпись и срок действия;
   - затем сертификаты приложения, worker'а и демона сравниваются побайтно.

   Форк не меняется, ослаблять проверку не нужно. Что из этого следует:
   - **Подлинность загрузки** по-прежнему подтверждает подпись minisign у `SHA256SUMS`, как у APK. Authenticode здесь
     нужен для того, чтобы демон узнавал своё приложение.
   - **SmartScreen** при установке покажет «неизвестный издатель». В инструкции к установке нужен отпечаток
     сертификата, чтобы его можно было сверить.
   - **Smart App Control** в Windows 11 в режиме блокировки не запускает файлы без доверенной подписи или репутации, а
     самоподписанный сертификат доверенным не считается. На такой машине установка не пройдёт. В инструкции нужно
     сказать, что Smart App Control придётся выключить. Если таких пользователей окажется много, это довод за купленный
     сертификат.
   - **Срок (`NotAfter`) — жёсткий предел.** `boxdd` сверяет срок самоподписанного сертификата с текущим временем и
     для самого демона при старте (`initializeServerIdentity`), и для приложения. Когда срок истекает, служба не
     стартует вообще: ни VPN, ни встроенного обновления. Метка времени при подписи не помогает: смотрится текущее
     время, а не время подписи. Отсюда:
     - срок сертификата берём с большим запасом, 10 лет и больше;
     - смена ключа требует ручной переустановки: встроенное обновление (`InstallUpdate`) сравнивает сертификат
       установщика с сертификатом установленного демона и отказывает с `SIGNER_MISMATCH`. Установщик с новым ключом
       пользователь запускает сам;
     - если нужна смена ключа без переустановки, это изменение форка (например, демон доверяет списку ключей) —
       отдельная задача с отдельным ревью.
   - **Хранение ключа.** Ключ хранится в секретах CI, как ключ подписи APK. Подписывает CI (`osslsigncode`), отпечаток
     публикуется в [TRUST.md](../TRUST.md).

   Этап 2b сертификата не требует, но идёт в режиме разработки: `boxdd run --listen 127.0.0.1:<порт>`. Это gRPC по TCP
   **без какой-либо проверки клиента**. Без `--listen` любой запуск, со службой или без, проверяет подпись и раскладку
   на named pipe. Поэтому:
   - слушать только `127.0.0.1`, никогда `0.0.0.0` или пустой адрес. Сам `boxdd` адрес не ограничивает: открывает
     любой и только пишет предупреждение в журнал. Поэтому демон в этом режиме запускается только скриптом этапа 2b,
     который отказывает во всём, кроме `127.0.0.1:<порт>`. В `nikod` та же проверка будет в коде;
   - только на машине разработчика;
   - в релиз этот режим не попадает: сборка релиза его отключает или проверяет, что флаг не используется.

   Как это сделано (2026-11-17):
   - скрипт — `desktop/tool/dev.dart`: берёт только номер порта и сам ставит перед ним `127.0.0.1`;
   - окно получает связь по TCP только при сборке с `--dart-define=NIKO_DEV=true`. Вся она стоит в одной ветке
     `main.dart` под константой времени компиляции: без флага компилятор выбрасывает ветку целиком, вместе с
     клиентом gRPC по TCP. `desktop.yml` собирает релиз без флага и проверяет, что слов этой ветки в сборке нет;
   - адрес в окне разбирает `DevEndpoint`: `127.0.0.1:<порт>` и ничего больше;
   - **в форке исправлен режим разработки на Windows** (`peer_windows.go`, `53abe2a`): по TCP у вызова нет
     проверенного клиента, и на Windows `boxdd` на это отвечал ошибкой всегда, так что `GetDaemonInfo` и
     `StartService` не проходили вовсе. Теперь при `--listen` клиент считается локальным, как на Linux. Канал
     named pipe не тронут.
2. **Транспорт Dart ↔ worker на Windows.** Worker слушает named pipe, а `dart:io` named pipe не умеет. Работают ли в
   `dart:io` unix-сокеты на Windows, надо проверить. Варианты:
   - **(а) Свой транспорт** для пакета `grpc` поверх named pipe через FFI. **Предпочтительный:** сохраняет проверку
     клиента, которую делает `boxdd`.
   - **(б) Worker на loopback TCP.** Это обход той же модели безопасности: любой локальный процесс, получивший доступ
     к порту, получает проверенный канал к демону, который работает с правами SYSTEM. Брать только если (а) не выйдет,
     и только с отдельным ревью безопасности. Обязательные условия:
     - токен передаётся только через stdin, не через командную строку и не через переменные окружения;
     - токен сравнивается за постоянное время;
     - принимается одно соединение;
     - перед приёмом PID клиента проверяется через `GetExtendedTcpTable`.

   Проверено на этапе 2b (`desktop/tool/probe_local_sockets.dart`, `desktop.yml`, run 43984838950, Dart 3.14):
   - **unix-сокет в `dart:io` на Windows работает** (`windows-latest`): слушать и подключаться можно; на Linux тоже;
   - named pipe как файл через `dart:io` не открывается (`\\.\pipe\…` — «The network path was not found»): без FFI
     до pipe не дойти.

   Отсюда третий вариант:
   - **(в) Worker слушает unix-сокет (AF_UNIX) вместо named pipe.** В Dart тогда нет ни FFI, ни своего транспорта:
     `grpc` умеет unix-сокеты сам. Проверка клиента остаётся на стороне worker'а, но PID клиента он берёт не у pipe,
     а у сокета (в Windows для AF_UNIX есть `SIO_AF_UNIX_GETPEERPID`; что он даёт всё нужное, надо проверить), и
     дальше проверяет процесс, родителя и подпись как сейчас. Это правка форка в месте, от которого зависит
     безопасность: только с отдельным ревью. Файл сокета должен лежать там, куда пишет только пользователь.

   Выбор между (а) и (в) — на этапе 3, вместе с выносом `boxdd` в пакет. (б) остаётся запасным.
3. **Где живёт код и один ли код экранов у Android и компьютера.** Разобрано в
   [PLATFORMS.md](../design/PLATFORMS.md). Решение владельца (2026-11-16): Android остаётся на Kotlin, компьютер —
   на Flutter, одинаковыми их делает общий слой (токены, тексты, API, описания экранов-списков), из которого обе
   стороны получаются генерацией. Пока — в этом репозитории: `desktop/`, `libcore/cmd/nikod`, `shared/`.
