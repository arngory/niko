# Niko для компьютера: дизайн и устройство

Рабочий документ этапа 2 десктопа. Требования к каждому элементу экрана, от интерфейса до ядра, ведутся в
[REQUIREMENTS.md](REQUIREMENTS.md); здесь — как мы работаем над дизайном, как устроено приложение и что ещё решить.

## Стек (решение владельца)

- **Интерфейс:** Dart + Flutter (Windows сначала, Linux потом). Electron не берём.
- **Демон:** `boxdd` из нашего форка ядра (служба Windows, gRPC). Сборка под Windows уже в CI (`desktop.yml`):
  `boxdd.exe`, `sing-box.exe`, `libcronet.dll`. naive под Windows проходит тесты.
- **Логика Niko:** Go. Пакеты `libcore/raysub`, `rayapi`, `rayprobe`, `probe`, `dnsprobe`, `stun`, `minisign` уже
  собираются и проходят тесты под Windows в том же CI.

## Как работаем над дизайном (pen.dev)

1. **Площадка:** pen.dev в браузере, workspace `wekweakin/shared`. Там рисует дизайн-сессия.
2. **Источник правды — файлы `.pen` в репозитории**, каталог `design/`. Формат `.pen` — JSON, поэтому изменения видны в
   `git diff`. После каждого раунда файл скачивают из pen.dev и кладут в `design/`.
   CLI `pen` (0.3.16) облачные файлы не открывает: он видит только список workspace и локальные `.pen`.
3. **Просмотр:** из `.pen` выгружаются PNG (масштаб 2) в `design/png/` командой `pen interactive --in design/<файл>.pen`
   и функцией `Export`. Ревью идёт по PNG и по этой матрице.
4. **Имена узлов = ID требований.** Каждый экран и элемент в `.pen` называется с ID из матрицы:
   `D07 Пинг`, `S03 Строка сервера`. По этим же ID ищется код во Flutter (`// D07`). Так видно, что нарисовано, что
   сделано и чего нет. Позже это сможет проверять скрипт в CI.
5. **Раунды:**
   1. **Каркасы** всех экранов из матрицы, чёрно-белые, без украшений.
   2. **Состояния:** первый запуск, подключение, ошибка, нет сети, подписка истекает, трафик исчерпан, служба не
      установлена.
   3. **Токены:** цвета, шрифты, отступы как переменные `.pen` с темами light/dark. Они один к одному переходят в
      `ThemeData` Flutter.
   4. **Компоненты:** кнопка питания, строка сервера, карточка узла, переключатель пресета, строка журнала. В `.pen`
      это reusable-компоненты, во Flutter — виджеты с теми же именами.
   5. **Тексты** на русском и английском. Ошибки называют причину и следующее действие.
6. **Правила для всех экранов:**
   - Цвет — не единственный признак: у пинга есть число, у ошибки есть значок и текст.
   - IP выхода не запрашивается сам. Только по кнопке, с предупреждением, что запрос уходит на внешний сервис
     (решение владельца).
   - Проверки сервисов тоже только по кнопке.

## Как устроено приложение

```
<install>\sing-box.exe (Flutter)
   │ named pipe
   ▼
<install>\resources\daemon\sing-box-daemon.exe worker      ← тот же файл, что и демон, подкоманда worker
   │ named pipe, проверка подписи и родителя
   ▼
<install>\resources\daemon\sing-box-daemon.exe (служба)
   ├─ boxdd: ядро, TUN, системный прокси
   └─ NikoService: профили, подписки, raycontrol, сборка конфига
```

- **Как `boxdd` проверяет клиента на Windows** (`experimental/boxdd/peer_windows.go`, `security_windows.go`):
  - Имена и каталоги заданы в коде. Демон — `sing-box-daemon.exe` в `<install>\resources\daemon\`, приложение —
    `sing-box.exe` в `<install>\`. Демон в другом месте не стартует.
  - Worker — это тот же исполняемый файл, что и демон, запущенный с подкомандой `worker`. Отдельную программу демон не
    примет.
  - Родитель worker'а должен быть установленным приложением.
  - Приложение, worker и демон подписаны одним сертификатом Authenticode.
  - Worker сам обслуживает `ApplicationService` и передаёт приложению проверенное соединение с демоном
    (`--daemon-relay-socket`).
- **Имена — задача этапа 3.** Когда `boxdd` выносится в пакет, либо параметризуем имена и раскладку в форке, либо
  называем файлы так, как ждёт `boxdd`. В любом случае `desktop.yml` сейчас кладёт ядро как `sing-box.exe`, а это
  имя `boxdd` ждёт у приложения. Ядро из CI нужно переименовать.
- **Почему Go для логики.** Всё, что должно работать в фоне без окна, живёт в службе: сторож, обновление подписок,
  адаптивность канала, отчёты. Окно Flutter может быть закрыто. Сейчас эта логика в Kotlin (около 6000 строк в
  `io.niko.raycontrol`) и в парсерах ссылок (около 7000 строк в `io.niko.fmt`). Переносим её в Go один раз; потом
  Android переходит на ту же Go-версию блок за блоком.
- **Как проверяем перенос.** Golden-тесты: один набор входов (ссылки, подписки, ответы узла) прогоняется через Kotlin и
  через Go. Сравниваются получившиеся профили и JSON конфига ядра. Пока Go не совпадает с Kotlin, Android остаётся на
  Kotlin.
- **Новый API.** `NikoService`: свой proto рядом с `boxdd`. `boxdd` сейчас `package main`, поэтому его службы нужно
  вынести в импортируемый пакет форка. Тогда `libcore/cmd/nikod` соберёт `boxdd` и `NikoService` в один бинарник
  демона (он же worker). Имена и раскладка — см. выше.

## Порядок работ

| Этап | Что | Готово, когда |
|---|---|---|
| 2a | Каркасы экранов, эта матрица | экраны из матрицы нарисованы, у каждого элемента есть ID |
| 2b | Проверка связки Flutter ↔ `boxdd` на Windows, режим разработки (см. «Что решить», п. 1) | кнопка запускает готовый JSON-конфиг, видны статус и скорость |
| 3 | `nikod` + `NikoService`: хранилище профилей, импорт ссылок и подписок, сборка конфига в Go | golden-тесты Go = Kotlin |
| 4 | raycontrol в Go: подписка узла, сторож, канал, отчёты, админ-вызовы | interop против `rayd` проходит для `nikod` |
| 5 | Установщик, подпись, обновления, трей, автозапуск | релиз Windows с проверкой, как у APK |
| 6 | Linux | — |

## Что решить

1. **Сертификат подписи Windows.** Нужен для релиза. `boxdd` принимает два вида подписи
   (`experimental/boxdd/authenticode_windows.go`):
   - **(а) Купленный** OV-сертификат или Azure Trusted Signing: цепочка до доверенного корня. SmartScreen не
     предупреждает.
   - **(б) Свой самоподписанный ключ проекта** с EKU codeSigning. `boxdd` уже принимает его как есть: проверяет
     самоподпись и срок действия, затем побайтно сравнивает сертификаты приложения, worker'а и демона. Форк не
     меняется, и ослаблять эту проверку не нужно. Минусы: SmartScreen предупреждает при установке, а когда срок
     сертификата (`NotAfter`) истекает, установленная версия перестаёт пускать приложение. Значит, ключ нужно
     менять заранее, с выпуском новой версии.

   Этап 2b сертификата не требует, но идёт в режиме разработки: `boxdd run --listen 127.0.0.1:<порт>`. Это gRPC по TCP
   **без какой-либо проверки клиента**. Без `--listen` любой запуск, со службой или без, проверяет подпись и раскладку
   на named pipe. Поэтому:
   - слушать только `127.0.0.1`, никогда `0.0.0.0`;
   - только на машине разработчика;
   - в релиз этот режим не попадает: сборка релиза его отключает или проверяет, что флаг не используется.
2. **Транспорт Dart ↔ worker на Windows.** Worker слушает named pipe, а `dart:io` named pipe не умеет. Работают ли в
   `dart:io` unix-сокеты на Windows, надо проверить. Варианты:
   - **(а) Свой транспорт** для пакета `grpc` поверх named pipe через FFI. **Предпочтительный:** сохраняет проверку
     клиента, которую делает `boxdd`.
   - **(б) Worker на loopback TCP.** Это обход той же модели безопасности: любой локальный процесс, получивший доступ
     к порту, получает проверенный канал к демону, который работает с правами SYSTEM. Брать только если (а) не выйдет,
     и только с отдельным ревью безопасности. Обязательные условия:
     - токен передаётся только через stdin, не через командную строку и не через переменные окружения;
     - токен сравнивается за постоянное время;
     - принимается одно соединение;
     - перед приёмом PID клиента проверяется через `GetExtendedTcpTable`.

   Проверяем на этапе 2b.
3. **Где живёт код.** Предлагаю этот репозиторий: `desktop/` для Flutter и `libcore/cmd/nikod` для демона. Общие
   libcore, CI и выпуск релизов.
