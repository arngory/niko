## 1. VLESS encryption на сервере

**В форке sing-box серверной части нет.** В `protocol/vless/encryption` лежит только клиент: `client.go`, `common.go`,
`xor.go`, `lx_*.go`. Его перенесли из sing-box-lx, а туда — из Xray. В `option.VLESSInboundOptions` нет поля
`decryption`.

**Решение: `inner` поднимается на Xray** (`arngory/xray-core`, закреплён в `.github/xray-interop.env`).

Совместимость именно этой пары уже проверяется в CI. Workflow `xray-interop.yml` поднимает Xray с
`decryption` = `mlkem768x25519plus` (вариант ML-KEM-768 из `xray vlessenc`), подключает к нему клиентское ядро
Niko и ждёт `204`. Последний прогон прошёл.

**Перенос сервера в форк возможен позже.** Источник — `proxy/vless/encryption/server.go` в Xray (лицензия MPL-2.0,
как у клиента). К нему нужно поле `decryption` в inbound vless. Делать перенос стоит только если понадобится убрать
Xray с ноды: по составу процессов это ничего не упрощает.

## 4. Нагрузочный тест

Не выполнен: `niko-server front` и `backend` ещё не написаны. Тест появится на R1 вместе с разделением процессов,
как job в CI:

- топология: фронт, бэкенд `hy2-masq` и бэкенд `naive` — отдельные процессы под разными UID;
- сценарий: 200 одновременных потоков через каждый мультиплексор, 10 минут;
- метрики: пропускная способность, p99 задержки, CPU фронта на гигабит, утечки горутин (`goleak`), RSS;
- сравнение UDP-пути: копия датаграмм через фронт и прямой `SO_REUSEPORT`. Если копия через фронт дороже 30 %
  CPU на гигабит — сообщаем и предлагаем `SO_REUSEPORT` + eBPF (классификация в BPF по тем же правилам udpmux).

## 5. Постквант для Yggdrasil

**Линк (сосед ↔ сосед).** У TLS-линков yggdrasil-go `MinVersion = TLS 1.3`, а `CurvePreferences` не задан
(`src/core/tls.go`). Поэтому действует умолчание Go, а в Go ≥ 1.24 оно включает гибрид `X25519MLKEM768`.
Ядро Niko и niko-server собираются на Go 1.25, значит линк между ними уже гибридный. На ноде бэкенд `yggdrasil`
задаёт `CurvePreferences = [X25519MLKEM768]` без отката, как Hysteria2 и naive. QUIC-линки используют тот же
`crypto/tls`, правило для них то же.

**Сквозное шифрование (узел ↔ узел).** ironwood шифрует сессии через NaCl box (X25519 + XSalsa20-Poly1305) с ключами
из ed25519. Это классическая криптография, и замена её на PQ ломает совместимость с сетью.

**Вывод для ноды.** По решению P-14 подключения к ноде только прямые: клиент — непосредственный сосед ноды. Значит
весь путь клиент → нода — это один TLS-линк с `X25519MLKEM768`, и трафик защищён постквантово. Сквозное
классическое шифрование работает внутри, как второй слой. Полезный трафик всё равно идёт в `inner` (VLESS
с ML-KEM-768), так что постквант есть и там. С публичными пирами (флаг) путь проходит через чужие узлы, и тогда
PQ даёт только `inner`.

## 6. Ссылки и подпись подписки

Предложение к R1; финальный формат задаёт `export` raycontrol (P-10).

### Ссылки

Обычные ссылки протоколов, которые клиент уже понимает: `vless://` (с `pqv=`), `hysteria2://`, `naive+https://`.
Плюс параметры Niko в query. Разбор этих параметров в клиенте добавляется вместе с импортом `rcdev1:`:

| Параметр | Значение |
|---|---|
| `niko-node` | `node_id` (32 hex) импортированной ноды: профиль получает SPA v2 этой ноды и её адрес |
| `niko-svc` | ID сервиса из карты `services` пакета регистрации — идёт в scope SPA |
| `niko-pin` | SHA-256 SPKI сертификата (base64url) — для `hy2-obfs` вместо `pinSHA256` |
| `niko-dns` | DNS-туннель: `dnstt;<резолвер>;<зона>;<pubkey>` или `masterdns;<резолверы через ,>;<зона>;<метод>` (ключ MasterDnsVPN — отдельно, `niko-dnskey`) |
| `niko-inner` | вторая ступень: ссылка `vless://` к `inner` (base64url), с `encryption=mlkem768x25519plus…` |

Ключ устройства в ссылки не попадает: он только в `rcdev1:` и в Android Keystore.

### Подписка

Ответ — JSON-конверт, а не base64-список, чтобы подпись покрывала всё:

```json
{
  "payload": "<base64url от JSON ниже>",
  "sig": {"ed25519": "<base64url>", "mldsa65": "<base64url>"}
}
```

```json
{
  "v": 1, "node_id": "<32 hex>", "seq": 42,
  "issued": 1767225600, "expires": 1767312000,
  "profiles": [
    {"svc": 1, "name": "reality", "link": "vless://…",
     "next": {"link": "vless://…", "from": 1767268800}}
  ]
}
```

- Подписываемое сообщение: `"raycontrol-sub-v1" ‖ payload` (байты до base64url).
- Подписи: Ed25519 и ML-DSA-65 (FIPS 204, пустой контекст). Клиент принимает подписку только если **обе** верны.
  ML-DSA-65 в клиенте уже есть (circl, проверка REALITY).
- Защита от отката: `seq` строго растёт, клиент хранит последний; `expires` ограничивает жизнь ответа.
- Ротация: `next` со временем `from`. Клиент держит обе ссылки и после `from` переключается на `next`, не разрывая
  текущие соединения. Если `next` не работает — возвращается к текущей до `expires`.
- Публичные ключи ноды нужно доставить в пакете регистрации. Предложение: новое необязательное поле в `rcdev1`:
  `"node_keys": {"ed25519": "<hex>", "mldsa65": "<base64url>"}`. Старые клиенты его игнорируют, формат остальных
  полей не меняется.

## 7. Предложение: SPA v2 поверх TCP

Вне вопросов раздела 6, но нужно решить до R1. Подробности — [`../research/anti-dpi.md`](../research/anti-dpi.md) §4.

**Проблема.** На мобильных сетях РФ часто режется весь неизвестный UDP, а TCP 443 проходит. Тогда пакет SPA v2 не
доходит, и нода недоступна целиком, хотя REALITY по TCP работал бы.

**Предложение: второй носитель — тот же пакет внутри TCP.**
- Клиент открывает TCP-соединение на порт текущего слота (тот же `port(slot)`), отправляет пакет SPA v2 без изменений
  первыми данными и закрывает соединение. Ответа не ждёт.
- Нода: на порты слотов `slot−1..slot+1` — nftables `synproxy` (рукопожатие без сокета) и NFLOG первого сегмента
  с данными в `rayspa`. Проверка та же, что для UDP (`spa-v2.md` §6), длина — по `len(payload)`. Затем RST.
  Кэш nonce общий для UDP и TCP.
- Клиент: сначала UDP, как сейчас. Если подключение после UDP-пакета и его повтора не удалось, — один раз TCP-носитель
  и снова подключение. Запоминать для сети, какой носитель сработал.
- Цена: порт слота отвечает на SYN (виден сканеру как открытый), но он меняется каждый слот и ничего не отдаёт.
  Ограничение частоты SYN на источник — в nftables, как для UDP.

Клиентскую часть сделаем, как только формат будет принят (одна функция отправки в `libcore/knock/spa2.go`
и порядок «UDP → TCP» при неудачном подключении).

## 9. Ответ на `niko-r4-note.md` (клиент Niko v1.14.0)

| № | Вопрос (§7) | Ответ |
|---|---|---|
| 1 | Перезапрос подписки, когда не работают ни `link`, ни `next` (§1.3) | **да, с v1.14.0** — механизм ниже |
| 2 | Импорт пакета: вставка, файл, QR (§4) | вставка и файл — да, токен `rcdev1:` ищется в любом тексте; QR — предложение ниже |
| 3 | Смена `sni` в `next`: кэши и пулы по имени | их нет: при смене профиля ядро перезапускается и строит исходящие заново; REALITY не возобновляет сессии; к ноде клиент идёт по её адресу, SNI есть только в ClientHello |

### Ротация в клиенте (§1)

- **Учётные данные.** Клиент хранит у каждого профиля оба значения: `link` и `next {link, from}`. Время `from` сверяется по
  часам ноды (поле `time` подписки), а не устройства.
- **Переключение в `from`.** Плановое обновление ставится на ближайший `from` или на 3/4 срока подписки. Если сеть есть,
  но нода в этот момент недоступна, профиль всё равно переходит на сохранённый `next.link`.
- **Текущие соединения не рвутся.** После плановой смены ядро продолжает работать со старыми данными. Проверка
  соединения идёт через 15 с, затем каждые 30 с в течение 3 мин. Ядро перезапускается только когда старые данные
  перестали работать. Поэтому при смене UUID (старый работает ещё 2 дня) разрыва нет, а при смене ключей REALITY
  перезапуск происходит в течение минуты после переключения на сервере.
- **Ни `link`, ни `next` не работают (§1.3).** Пока ядро работает с профилем ноды, клиент проверяет его тем же тестом
  соединения (`generate_204` через основной исходящий):
  - когда проверки идут: через 20 с после запуска, через 15 с после смены сети и раз в 10 мин; без сети проверок нет,
    а на новой сети паузы между перезапросами начинаются заново;
  - после двух неудач подряд клиент **сразу** перезапрашивает подписку и перезапускает ядро, если профиль изменился;
  - если подписку получить не удалось, профиль переключается на другие данные (`link` ↔ `next`, §1.2), если они есть;
    на `next` — не раньше чем за 2 мин до `from` по часам ноды;
  - перезапросы после неудач идут с паузой от 5 мин до 1 ч.
- **Отказ ноды.** Если нода отказала устройству (не знает его или подписи не сходятся), плановые обновления
  останавливаются, и клиент просит импортировать пакет заново. Несовпадение pin останавливать нельзя: его даёт любой
  TLS-посредник на пути. Поэтому при нём клиент просто повторяет запрос.

### Требования к пакетам (§3) — выполнены

- SPA по UDP — одна датаграмма длиной из `len_min..len_max`, через обычный сокет, без IP-опций. TCP-носитель передаёт
  пакет одной записью.
- QUIC Hysteria2 идёт с DF: quic-go ставит его сам, а обёртка UDP-desync выставляет `IP_MTU_DISCOVER` = probe.
  Фейковые датаграммы перед QUIC идут через тот же сокет. Дробление ClientHello против DPI делит его на TCP-сегменты,
  а не на IP-фрагменты.
- Тесты клиента не печатают пакеты `rcdev1:`, даже тестовые.

### QR: пакет без ключей ноды

> **Снято** после [`niko-r3-note.md`](https://github.com/arngory/raycontrol/blob/claude/clever-feynman-w0e2v1/docs/handoff/niko-r3-note.md) §3: для QR служит приглашение `rcinv1:` (~600 символов),
> а `rcdev1:` устройство получает по API. Поле `node_keys_sha256` не нужно. Текст ниже оставлен для истории.

Сейчас пакет занимает ~4 КБ и в QR не помещается. Предложение `rcdev1` v1 без новой версии: необязательное поле
`node_keys_sha256` вместо `node_keys`.

- **Само поле:** `node_keys_sha256` = hex SHA-256 от `ed25519 (32 байта) ‖ mldsa65 (1952 байта)`.
- **Как клиент получает ключи:** при импорте он забирает их по каналу подписки — `GET /sub/v1/keys`. Авторизация та же,
  что у `/sub/v1`: SPA, закреплённый pin, заголовки `X-Raycontrol-Device` и `RC1`. Ответ:
  `{"ed25519": "<hex>", "mldsa65": "<base64url>"}`. Клиент принимает ключи, только если хэш совпал. Подлинность ключей
  обеспечивает хэш из пакета, а не TLS.
- **Размер:** пакет ~1 КБ (QR версии ~27, коррекция M).
- **Совместимость:** при `node_keys` всё работает как сейчас. Пакет с `node_keys_sha256` старый клиент отклонит с
  понятной ошибкой («sub without node_keys»).

Клиентскую часть сделаю, как только raycontrol примет формат.

## 13. Адаптивность канала: что нужно от сервера

Клиент начинает подстраиваться под канал. Первый этап делается без сервера:
- короткие зонды через туннель каждого профиля ноды: доступность, RTT, время до первого байта, зависание TCP
  (после скольких байт поток встал), UDP через DNS-запрос;
- выбор профиля ноды по оценке, с защитой от метаний;
- память результатов по сети: тип сети и оператор, хранится только на устройстве.

Скорость и потери так честно не измерить: сторонние цели меряют не тот путь и ограничивают нагрузку.
Для этого нужен сервер. Ниже предложения; формат и спецификацию (`docs/spec`) определяет raycontrol.

1. **Сервис замера в `rayd`**, только для устройств ноды, с той же авторизацией, что api-v1 (клиентский
   сертификат), или с токеном из подписки.
   - TCP: поток заданного объёма вниз и приём заданного объёма вверх. В ответе — сколько байт и за какое время.
   - UDP: эхо с номером и временем отправки, как в irtt. Даёт RTT, джиттер, потери и переупорядочивание.
     Размер пакета задаёт клиент: так проверяется и MTU.
   - Ограничения: не больше 30 с на замер, один замер на устройство одновременно, суточный объём на устройство.
   - Доступ двумя путями, чтобы отличать канал от туннеля:
     - как назначение внутри туннеля каждого профиля: имя или адрес, который Xray и `rayd naive` отдают
       сервису;
     - напрямую после SPA.
2. **Метрики соединения со стороны сервера** в api-v1, для текущих соединений устройства. Сервер видит то, чего
   не видит клиент: RTT и переотправки из `TCP_INFO`, потери QUIC у Hysteria2. Например,
   `DeviceService.GetLinkStats`.
3. **Подсказки в подписке** — необязательные поля v1, по §6 `niko-r3-reply.md` это допустимо без новой версии:
   - рекомендуемый порядок профилей;
   - диапазоны портов.
4. **Сводка от клиентов** («из сети X не проходит UDP», «TCP встаёт после 16 КБ») — позже, только с согласия
   пользователя и без данных, которые его выдают. Обсуждаем отдельно.

5. **Brutal для Hysteria2 на приёме клиента.** Клиент будет задавать темп Brutal по замеру, отдельно для
   отдачи и приёма: на мобильной сети они сильно различаются.
   - Отдача: клиент задаёт свой темп сам. Сервер ограничивает его только через `brutalDown`: это значение
     уходит клиенту в ответе (`Hysteria-CC-RX`), и клиент шлёт с темпом min(`brutalDown`, свой темп).
   - Приём (сервер → клиент): темп, переданный клиентом в `Hysteria-CC-RX`, Xray берёт, только если у
     inbound в `finalmask.quicParams` (`transport/internet/hysteria/hub.go`):
     - `congestion` не задан или равен `"brutal"`. При `"bbr"` и `"reno"` темп клиента не используется,
       а при `"force-brutal"` сервер шлёт с темпом `brutalUp` всем подряд и перегружает медленные каналы;
     - `brutalUp` задан. При 0 всегда BBR; меньше 64 КиБ/с конфиг не загрузится.

     Сейчас ничего из этого не задано, и приём клиента всегда идёт на BBR.
   - Просьба:
     - задать `brutalUp` как потолок на одно соединение: ёмкость канала ноды или лимит тарифа;
     - `congestion` оставить пустым или `"brutal"`;
     - `brutalDown` задавать, только если отдачу клиентов нужно ограничить.

     Сервер тогда шлёт с темпом min(`brutalUp`, темп клиента). Клиент без оценки для своей сети темп не
     передаёт, и для него остаётся BBR.
   - Метрики из п. 2 для Hysteria2 (потери и подтверждённая доля у серверного Brutal) помогут клиенту
     вовремя снижать темп.

### 14.2. Неясности в `probe-v1.md`

1. **`link` во время замера (§4.1, §5).** Можно ли вызывать `GET /probe/v1/link`, пока открыта сессия UDP или идёт

3. **Протокол HTTP.** Trailer `Probe-Result` у `down` предполагает h2 или chunked HTTP/1.1. Эндпоинт объявляет в ALPN
   `h2`? Клиент будет просить `h2` и `http/1.1` и читать trailer в обоих случаях.
4. **Через туннель (§1.1)** клиент делает как образец `internal/xrayapi/probe_test.go`: адрес и SNI —
   `probe.raycontrol.invalid:443`, пин `sub.pin`, авторизация та же. Если SNI должен быть другим, поправьте.

### 14.3. Сводка от клиентов (§13 п. 4): предложение формата

**Что клиент готов отдавать**, только с явного согласия. По умолчанию выключено. В настройках перед включением
показан пример того, что уйдёт.

- **Только о текущей сети и только из неё.** Отчёт уходит напрямую на эндпоинт подписки из той сети, о которой он.
  Тогда нода сама определяет ASN и страну по адресу запроса в момент приёма и адрес не хранит. Клиент не
  связывает в одном отчёте разные сети: у ноды нет способа узнать, что домашний Wi-Fi и мобильный оператор принадлежат
  одному человеку.
- **Не чаще раза в сутки на сеть**, в случайный момент и без времени наблюдений. В отчёт идут только результаты
  зондов, которые клиент и так делал (переключение при сбое, «Проверить канал»): ради отчёта зонды не запускаются.
- **Без идентификаторов.**
  - Ни ID устройства в теле, ни хэша сети клиента, ни адресов, ни имён сетей.
  - Заголовок `X-Raycontrol-Device` нужен для `RC1`. Предлагаем, чтобы нода брала его только для лимита и веса и
    не хранила вместе с данными.

```
POST /probe/v1/report
{"v": 1,
 "net": "cellular",          // cellular | wifi | ethernet | other
 "mcc_mnc": "25001",         // только cellular: MCC и MNC сети, в которой зарегистрирован телефон (Android отдаёт без разрешений)
 "obs": [
   {"svc": 3, "kind": "reality",   // svc — ID сервиса ноды; kind — вид профиля из подписки
    "result": "works",             // works | degraded | fails
    "tcp_stall_kib": 16,           // поток встал: порог, округлённый вниз до степени двойки (8, 16, 32, 64, 128); нет — поле отсутствует
    "udp": "0-1",                  // потери UDP, %: 0-1 | 1-5 | 5-20 | 20-50 | 50-100 | none (UDP не проходит); не мерили — поля нет
    "mbps": "5-20"}                // скорость вниз через туннель: <1 | 1-5 | 5-20 | 20-100 | 100+
 ]}
```

- `degraded` — TCP работает, но было хотя бы одно из трёх: поток вставал, скорость < 1 Мбит/с, потери UDP > 20 %.
- В `obs` по одной записи на `svc`, не больше 16.
- Ответ — `204`; `429`, если отчёт о сети за эти сутки уже был.

**Чего клиент не отдаёт:** точные числа (RTT, скорости, байты), время, порядок, в котором профили пробовались,
историю сетей, выбранный профиль.

### 14.4. Подсказка о порядке профилей (§13 п. 3): какие сигналы нужны клиенту

- **По сети запроса, а не списком на все случаи.** Подписку клиент берёт напрямую, поэтому нода знает ASN адреса
  запроса и может положить подсказку только для него. Клиенту не нужно знать свой ASN, а ноде — хранить чужие
  сопоставления.

  ```json
  "hints": {"order": [3, 5, 4], "avoid": [4], "devices": 23, "days": 7}
  ```

  - `order` — порядок сервисов.
  - `avoid` — сервисы, которые в этой сети чаще не работают.
  - `devices` и `days` — на скольких устройствах и за сколько дней получено.
- **Как клиент её применит.**
  - Только как начальный порядок для сети, о которой у него нет своих результатов.
  - Свои свежие результаты главнее подсказки.
  - Подсказку при `devices` меньше порога (k) клиент не ждёт: такую нода не отдаёт вовсе.
- **Что поможет кроме сводки.** Отдельные признаки по видам: у сети не проходит UDP вообще; TCP встаёт на одном и
  том же пороге. Для них в `hints` нужны поля `udp_blocked` и `tcp_stall_kib`. По ним клиент заранее включит
  средства против DPI (фрагментацию TLS, UDP-desync) или сразу пойдёт в TCP-профиль.

- CI против настоящего `rayd` v0.8.0: подписка несёт `probe.report: ["udp_mtu"]`; 10 отчётов с полем дают
  `hints.udp_mtu`.

**Прочее с прошлого ответа.**
- v1.24.1: длина UDP считается свойством сети, только если все длины до неё измерены. `429` с долгим
  `Retry-After` (исчерпан суточный объём) отличается от идущего замера.
- Пиры Yggdrasil `tcp`, `ws`, `socks` клиент берёт только после `tls`, `quic`, `wss`.
- В CI-задаче `supervised` добавлены DNS-туннели: dnstt и masterdns через фронт ноды на UDP 53, до `inner`.

**§3 п. 2 — VPS-CHECK** ждём ноду.

## 22. Предложения серверу по итогам ревью (2026-11-04)

Полное ревью — [`../REVIEW-2026-11.md`](../REVIEW-2026-11.md). Ниже два предложения именно для стека raycontrol;
оба по ресёрчу блокировок 2025–2026 (§2 ревью).

### 22.1. Вход через российский узел: цепочка нод и детектор белого списка

**Зачем.** Две главные угрозы сейчас — свойства пути, а не протоколов:
- на мобильных сетях TCP к зарубежным хостингам замирает после ~16–20 КБ;
- в режиме белого списка доступны только разрешённые IP/CIDR, а UDP 443 и UDP 53 режутся.

Ни REALITY, ни Hysteria2, ни SPA с этим ничего не сделают. Сообщество (Habr, net4people #490, #516) сходится на одном:
вход через узел в России, лучше в AS из белого списка, дальше — к зарубежному выходу.

**Предложение.**
1. **Роль `relay` у ноды.** Второй узел (российский VPS) с минимальной установкой: фронт niko-server, который
   пересылает TCP 443 и UDP 443 на выходную ноду на уровне L4, без своих ключей сервисов.
   - REALITY, Hysteria2 и naive остаются сквозными до выхода, на relay нет ничего, что можно расшифровать.
   - У relay своё SPA: стучатся к нему.
   - Выходная нода пускает адрес relay постоянно, без SPA. Иначе она увидит источником relay и не узнает
     устройство.
   - `rayctl relay add <host>` на выходе: выдаёт relay его конфиг и ключи SPA.
2. **Подписка** несёт relay как альтернативный адрес профиля, например `relays: [{"host": …, "sub_pin": …,
   "spa": …}]` и `profiles[].via: "relay-1"`.
   - Клиент строит тот же профиль с адресом и SPA relay.
   - Переключение идёт и по пути: напрямую или через relay. Watchdog у клиента это уже умеет для профилей.
3. **Детектор белого списка — замер на relay.** Эндпоинт `probe-v1` на relay, к которому клиент ходит напрямую.
   - Если relay отвечает, а выход напрямую нет, это режим белого списка (или заморозка): клиент сразу берёт путь
     через relay и не тратит время на зарубежные профили.
   - В сводке это видно как отдельная корзина (поле `path`: `direct` или `relay`, через `probe.report`, как
     `udp_mtu`).

**С клиентской стороны.** Профили-цепочки в Niko есть (ChainBean). Добавлю `via` в разбор подписки, SPA к relay и
переключение «напрямую ↔ через relay» в watchdog, как только появится формат.

### 22.2. Убрать отпечатки на стороне ноды

1. **Сертификат сайта-приманки и ML-DSA-65.**
   - По документации Xray (REALITY), временный сертификат с ML-DSA-65 больше обычного. Если цепочка настоящего
     сайта-приманки меньше ~3500 байт, разница в размере — отпечаток.
   - Предложение: `rayctl check` и `service cert` предупреждают о цепочке меньше порога. В инструкции — RSA-цепочка
     или цепочка с промежуточным. Проверка в тесте установки, как `xray tls ping`.
2. **Закрытый TCP 443 при живых TLS-сессиях — аномалия.**
   - Сейчас 443 закрыт до SPA. Сканер видит «хост молчит на 443», а DPI видит, что к нему же идут TLS-сессии
     с отдельных адресов.
   - Предложение: опция держать TCP 443 открытым для всех. Неавторизованным REALITY self-steal отвечает как сайт,
     для этого он и сделан. SPA тогда закрывает только остальное: UDP 443, порт API, порт подписки.
   - Компромисс: активное зондирование 443 становится возможным. REALITY к нему устойчив, а naive, DoH и Yggdrasil
     за фронтом нужно проверить на поведение при зондировании.
3. **Форма TCP-носителя SPA.**
   - 96–160 случайных байт первым пакетом TCP — ровно класс, который GFW режет с 2023 года (USENIX Security '23).
     По ТСПУ данных нет.
   - Предложение: носитель в форме TLS-записи — заголовок `16 03 01`, длина и тело, похожее на ClientHello. SPA
     внутри полей случайного вида (`random`, `session_id`, расширение).
   - Тогда стук TCP-носителем выглядит как обычное начало TLS.
4. **Мелочь.** Порог nftables по SPA на источник стоит проверить на всплеск при смене слота: несколько дозвонов
   клиента сразу. Клиент со своей стороны объединяет повторы с 1.26.0: параллельные дозвоны, сорвавшиеся на смене
   слота, шлют один повтор на всех.

Что из этого берёте, а что нет — по вашему решению. На клиенте 22.1 даёт больше всего; 22.2 п. 1 — дешевле всего.
